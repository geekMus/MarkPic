# 性能迭代记录

这份文件记录每一轮性能优化的**测量方法与前后数字**。所有数字都由 `tools/bench`
（造夹具 + 假图床）与真实 PicGo 现测得出，可以重跑复现。

## 怎么复现

```powershell
# 假图床：300 篇文档 × 每篇 30 处本地引用 × 图片池 60 张 × 8 KB 正文（约 2.8 MB）
go run ./tools/bench -bench both -files 300 -refs 30 -pool 60 -kb 8 -prose 8 -repeat 21 -verify

# 换成真实 PicGo（会真的上传，注意图床额度）
go run ./tools/bench -bench e2e -endpoint http://127.0.0.1:36677 -files 3 -refs 5 -pool 4 -kb 1 -verify

# 拆分阶段：只扫描分类（不写盘、不上传）
go run ./tools/bench -bench e2e -dryrun -files 300 -refs 30 -pool 60 -kb 8 -prose 8 -repeat 21
```

`-fresh` 表示每轮开始前删掉上次的输出（量「首次写入」），不加则是覆盖已有输出。
`-cpuprofile` / `-memprofile` 交给 `go tool pprof` 看热点。

## 测量环境

- Windows + Go 1.24，本地 SSD；夹具目录在 `%TEMP%`。
- 机器上有杀毒软件的实时防护，**首次创建文件的耗时会飘**（最好值 50 ms，偶尔冲到 320 ms），
  所以每轮跑 21 次，看最好值与中位数，别只看单次。
- 假图床是进程内的 `httptest` 服务器，网络耗时可以忽略；真实图床的数字另列一节。

## 第 0 轮：基线

夹具：300 篇 / 9600 处引用 / 2.8 MB，并发 4。

| 指标 | 数值 |
| --- | --- |
| 端到端墙钟 | 182 ms |
| 吞吐 | 1648 篇/s · 52 725 张/s |
| 峰值堆 | 12.0 MB |
| 累计分配 | 32.8 MB |
| 纯解析 | 297 MB/s · 14 700 allocs/遍 · 6.31 MB/遍 |
| 事件数 | 7605 |

CPU 剖析（`go tool pprof -top`）显示：`runtime.cgocall` 占 78%（Windows 上所有系统调用
都走这条），其中 `os.Stat` 累计占 27%，而我们自己的解析 `mdscan.ScanLang` 只占 3.6%。
**结论：这一轮该省的是系统调用，不是算法。**

## 第 1 轮：少发系统调用（e2e 182 ms → 92 ms）

1. **同一路径的存在性检查只做一次**。原来每个图片引用都要 `os.Stat` 一次：一篇文档里
   同一张图被引用 30 次，就有 30 次 stat；9600 处引用实际只有 60 个不同的文件。
   改成按小写绝对路径缓存（`Runner.fileExists`），stat 从 9600 次降到 60 次。
2. **预扫并行化**。`run.started` 事件要带上每篇文档的图片数，原来这一步是串行读+解析
   所有文件，真正开始转换前先白等一遍；改成按并发数并行（至少 4 路）。
3. **写盘后不再多删一次**。`writeAtomic` 改名成功后临时文件已经不存在了，原来仍会
   `os.Remove` 一次（Windows 上要多花一次系统调用才报错）。

| 指标 | 第 0 轮 | 第 1 轮 | 变化 |
| --- | --- | --- | --- |
| 端到端墙钟 | 182 ms | **92 ms** | −49% |
| 吞吐 | 1648 篇/s | **3258 篇/s** | ×2.0 |
| 峰值堆 | 12.0 MB | 11.2 MB | −7% |
| 纯解析 | 297 MB/s | 297 MB/s | 未动 |

## 第 2 轮：新文件直接写（92 ms → 50 ms）

先用一个独立的小程序量了各种写法的代价（300 个 9 KB 文件，取 5 轮最好值）：

| 写法 | 每个文件 |
| --- | --- |
| 临时文件 + 改名（原实现） | 0.298 ms |
| 直接写（`os.WriteFile`） | 0.084 ms |
| `OpenFile(O_CREATE\|O_WRONLY\|O_TRUNC)` + 写 + 关 | 0.089 ms |
| 覆盖已有文件 + 改名 | 0.317 ms |
| 覆盖已有文件（直接写） | 0.083 ms |

原子写比直接写贵 **3.5 倍**，而绝大多数输出都是**新文件**（旁路模式旁边没有同名文件）。
所以改成：

- 目标不存在 → `O_CREATE|O_EXCL` 直接建了写（顺便保证不覆盖别人刚写的文件）；
- 目标已存在 → 仍然「临时文件 + 改名」，中途失败不会把原文件写坏——原地替换模式下
  那个「原文件」就是用户的源文档，这一步不能省。

再加一条：**内容一模一样就不重写**。目标已存在时先比一下内容，相同就直接跳过，
重复跑一次不会白改一遍文件时间戳（对 rsync / 编辑器 / git 都友好）。

| 场景 | 墙钟（最好 / 中位） | 吞吐 |
| --- | --- | --- |
| 基线（第 1 轮） | 92 ms | 3258 篇/s |
| 首次写入 | **50 / 51 ms** | **6037 篇/s · 19.3 万张/s** |
| 覆盖已有输出（内容相同 → 跳过写入） | **32 / 34 ms** | **9376 篇/s** |
| 只扫描分类（不写盘、不上传） | 16 / 17 ms | 18 624 篇/s |

并发扩展（假图床，假图床在 4 路就饱和了）：1 → 198 ms，2 → 152 ms，4 → 141 ms，
8 → 148 ms，16 → 150 ms。

## 真机 PicGo 验证

`http://127.0.0.1:36677`，每张图约 1 KB。既验功能也对并发做测量。

**功能**：3 篇文档 21 处引用（含远程图、行内代码、围栏代码块、缺失图片、反斜杠路径写法）
→ 输出 3/3 篇全部替换、残留本地引用 0、远程/代码块/缺失各保留 3/3、原文件一字节未动；
替换后的真实地址形如 `https://webp.mus.pp.ua/test_storage/20261109014515208.png`。

**并发（这是本轮最值钱的发现）**：

| 并发 | 图片数 | 墙钟 | 每张 |
| --- | --- | --- | --- |
| 1 | 8 | 4.948 s | 618 ms |
| 4 | 8 | 1.744 s | 218 ms |
| 8 | 8 | 1.585 s | 198 ms |
| 16 | 24 | 1.568 s | **65 ms** |

上传是纯等网络，`concurrency` 就是「同时在飞的请求数」。旧默认值 4 明显偏低，
8 相对 4 已经能省下可观时间，16 在图多时还能继续拉开（约 9 路有效并行后趋于饱和，
说明瓶颈在 PicGo/图床那一侧）。

## 第 3 轮：默认并发 4 → 8

- `internal/settings/settings.go`：`DefaultConcurrency = 8`；`Default()` 用它。
- 设置文件加 `schemaVersion`（当前 2）。加载到没有该字段的旧设置时做一次性迁移：
  并发仍是旧默认值 4 的，提到 8，然后写回。**迁移过之后用户再手动改回 4 就不会被动。**
- 前端占位默认值、CLI 帮助文案同步。

真实图床上的收益（同一批图，同一台机器）：并发 4 → 218 ms/张，并发 8 → 198 ms/张，
并发 16 → 65 ms/张。

### 顺带修掉一个用户数据级的 bug：设置文件带 BOM 就整份失效

`Load()` 原来把文件字节直接喂给 `encoding/json`，而 json 见到 UTF-8 BOM 会直接报错 →
凡是手工编辑过 `settings.json` 的用户（记事本保存 UTF-8 带 BOM，PowerShell 的
`Set-Content -Encoding UTF8` 也带 BOM），**所有设置会被静默重置成默认值**：
界面能打开、也不报错，只是选项悄悄变回了默认。现在 `Load()` 先过 `trimBOM()` 再解析，
`hasSchemaVersion()` 与 `migrate()` 吃的是同一份去过 BOM 的字节（否则迁移会反复触发），
并补了一条 `TestStoreToleratesBOM` 把这个行为钉死。

## 第 4 轮：上传结果缓存（重复运行不再重传）

**动机（真机测出来的）**：6 篇文档、59 处引用、39 张 150 KB 的图（共 8.85 MB），
第一次跑 **13.793 s**；把输出删掉再跑一次，**13 s 又全部重传了一遍**——
「改一篇文章、再跑一次」是最常见的用法，而每次都在重传没变过的图片。

**做法**（`internal/uploadcache`）：按「图床地址 + 图片绝对路径」记下上次得到的 URL，
图片的**大小与修改时间都对得上**才算命中；地址存在 `data/upload-cache.json`，
保留最近 4000 条、30 天过期（图床上的文件可能被删，过期就重传）；写盘时与磁盘上的
现有内容合并（界面与命令行可能同时开着）。设置里「复用上次的上传结果」默认开启，
命令行 `--no-reuse` 关掉，关掉时既不读也不写这个文件。

| 场景（假图床，300 篇 / 9600 处引用） | 墙钟 | 上传 | 复用 |
| --- | --- | --- | --- |
| 冷启动（无缓存） | 55 ms（最好），首轮 218 ms | 59 | 0 |
| 热启动（有缓存） | **53 ms** | **0** | **59** |

| 场景（真机 PicGo，6 篇 / 39 张去重图 / 59 处引用 / 8.85 MB） | 墙钟 |
| --- | --- |
| 冷启动（无缓存） | 13.793 s（同一配置另一次 27.656 s——图床波动很大，报数要带区间） |
| 同一进程热轮 | **10 ms → 2 ms** |
| **跨进程热启动**（新进程 + 同一个缓存文件，即「改一篇文章再跑一次」） | **3 ms** |

每次热启动的 `-verify` 都是 `输出文件=6 已全部替换=6/6 残留本地引用=0 远程保留=6/6
代码块保留=6/6 缺失保留=6/6`，而且缓存命中的地址照样写进了输出——**13.8 s → 3 ms 是
这一轮最大的一笔**。顺带一次 200 篇 / 4340 处引用 / 3856 次上传的真机跑：18.429 s、
`-verify` 200/200 全绿。

**踩到的坑（值得记）**：第一版把「跨运行缓存」的判断放在「本轮去重表」**之前**，
于是同一张图本轮第一次上传后立刻写进缓存，后续引用就被当成「缓存命中」——
冷启动那一轮报出 `reused=6853`（≈9600 处引用里所有同轮去重），数字完全失真。
正确顺序是：**先问本轮去重表（命中=复用），只有本轮第一个碰到这张图的 goroutine
才去问跨运行缓存（命中=缓存）**。修完冷轮 `reused=0`、热轮 `reused=去重图片数`，
并有 `TestUploadCacheSkipsSecondRun` / `TestUploadCacheDisabledBySettings` 钉住。

## 命令行这一侧已经到地板了

修完缓存顺序 bug 之后重新量了一遍（假图床，300 篇 / 9600 处引用 / 2.8 MB / 并发 8）：

| 场景 | 墙钟（中位） | 吞吐 |
| --- | --- | --- |
| 首次写入（`-fresh`，真建 300 个文件） | 122 ms | 2547 篇/s |
| 输出已存在且内容一致（跳过写入） | 35 ms | 9158 篇/s |
| 只扫描分类（`-dryrun`，不写文件） | 18 ms | 18290 篇/s |
| 纯解析（不写、不传） | 9.6 ms | 295 MB/s |

**首次写入多出来的那 85 ms，全是「建 300 个文件」的钱**（0.28 ms/个，见第 2 轮的
写盘微基准），解析占 10 ms、上传占 17 ms。并发扩展 1 → 149 ms，2 → 118 ms，
4/8/16/32 都是 117–118 ms：**并发 2 就饱和**，再加只是让峰值堆从 17.5 MB 涨到 28.3 MB。
`-cpuprofile` 也印证了这一点：`runtime.cgocall` flat 82.79%、
`internal/conv.createExclusive` cum 74.37%，而我们自己的代码最贵的是
`mdscan.protectedMask` 1.16% 和 `mdscan.ScanLang` 1.06%（cum 3.97%）。
**写文件被系统/杀毒实时防护串行化了，算法侧没什么可榨的。**

## 第 5 轮：命令行早就跑完了，是界面上不去

### 挖出来的真 bug

300 篇 / 每篇 32 张图 / 9528 处引用，图床用假图床（每张 5 ms）：命令行那一侧几百毫秒
就跑完（300/300 个输出文件写好、上传缓存 59 条、假图床计数停在 59、进程 CPU 冻结），
但**界面永远停在「转换中」**：取消按钮还在，状态统计停在「部分失败 248 / 待转换 44 /
上传中 8」，展开的文件明细也是残缺的。

根因在服务端的事件枢纽：每个订阅者是一个 **cap 512** 的 channel，投递用的是
`select { case ch <- ev: default: /* 前端读得慢就丢 */ }`。9500 条事件灌满 512 之后，
**连 `run.finished` 这种终止事件也会被丢掉**，前端于是永远等不到「结束」——
浏览器端被每张图一条的进度事件淹没了。

### 修法

1. **进度事件按文件合并**：每个订阅者只留「每个文件最新的那一条进度」，攒到要发别的
   事件（或读走）时按文件顺序落进队列，`file.finished` 永远不会排在自己的进度前面。
2. **终止事件永不丢**：队列到 4096 上限时从最旧的开始丢，但跳过
   `run.finished` / `run.cancelled`。
3. **一批事件一次写、一次 flush**：原来每条事件一次 `Fprintf` + `Flush`。
4. **前端按 16 ms 一批应用**（`setTimeout`，不是 `requestAnimationFrame`——窗口最小化
   时 rAF 不跑，定时器会跑，事件不会闷在缓冲里）。

### 复测（同一个 300 篇夹具，打包版 exe）

| 指标 | 修之前 | 修之后 |
| --- | --- | --- |
| 界面 settle | 永不到达（卡在进行中） | **432 ms** |
| 浏览器收到的 SSE 事件 | 9528 条且互相挤掉 | **1433 条** |
| 帧间隔 | — | 133 帧，最大 140 ms，只有 1 帧 > 100 ms |
| 最终数字 | 「替换 7500 · 复用 7239 · 失败 366」 | 「9600 张图 · 替换 8855 · 失败 445」，与命令行逐位一致 |

第二次（缓存热启动）**351 ms** settle，footer 多出「复用 59」，上传 0 次。
取消路径也复测了：慢图床（400 ms/张）跑到一半点取消，**13 ms** 界面就落定为
「已取消」。

回归钉在 `internal/server/hub_test.go`：客户端全程不读时终止事件仍在、进度只留最新的
那一条、丢最旧的也不会丢终止事件、退订后再推不 panic。

## 第 6 轮：默认并发 8 → 16（真机图床上的 2 倍）

上一轮把默认并发从 4 提到 8 时，手上只有 1 KB 的小图。这一轮换成真实尺寸
（150 KB，6 篇文档 / 59 张去重图）重新扫了一遍并发，用的是真 PicGo：

| 并发 | 最好 | 中位 | 每张 |
| --- | --- | --- | --- |
| 4 | 14.474 s | 14.807 s | 245 ms |
| 8 | 12.128 s | 12.825 s | 206 ms |
| **16** | **4.818 s** | **5.064 s** | **82 ms** |
| 24 | 4.802 s | 5.070 s | 81 ms |
| 32 | 5.012 s | 11.349 s | — |

交叉复测（8/12/16/20 各跑 3 轮、每轮 2 次取最好）也指向同一个结论：
8 → 8.8/9.2/10.0 s，12 → 5.9/7.9/8.9 s，**16 → 5.6/6.2 s**（另有一次 26 s 的离群），
20 → 5.3/5.7/6.0 s。**16 是拐点，再往上不多拿速度、只是在压图床**；并发 32 已经开始
抖动（出现 30 s 的轮次）。

远端图床本身的方差很大（中位能跳到 30 s 以上），所以这里看的是「最好」这一列——
它是我们能达到的地板。

`CurrentSchemaVersion = 3`，`migrate()` 把「还是上一版默认值」（4 或 8）的旧设置
提到 16（迁移写回后再改回去就不会被动）；CLI 帮助、界面输入上限、`docs/API.md`
与 `README.md` 的参数表同步。
## 第 7 轮：把界面拖进快车道（1000 篇不再卡顿）

前面几轮量的都是「解析 + 上传 + 写盘」，从第 5 轮开始发现：**图形界面下，浏览器那一侧
才是整条链路的瓶颈**。这轮专门量它、改它。

### 夹具与跑法

`%TEMP%\cmp-gui-1000`：1000 篇文档 / 每篇 12 处引用 / 共 12000 张图（`tools/bench -files 1000
-refs 10 -pool 60 -kb 4 -prose 2 -dryrun -keep`）。假图床 `tools/mockpicgo`（每张 5 ms），
界面用打包版 exe 起在 17982 端口，数据目录另给（`CMP_DATA_DIR`），
探针脚本 `tools/perf/gui-1000.mjs`（用 Playwright 的 `browser_run_code_unsafe` 跑：
把文件放到 MCP 允许的目录、脚本写成 `async (page) => {...}` 表达式）。

### 改之前

一次运行：**settle 1586 ms**，浏览器侧收到 4612 条 SSE，最长帧间隔 **489 ms**，5 帧超过 100 ms，
JS 堆 38.1 → 60.5 MB。卡顿的根源在 `web/src/composables/useRun.ts`：

- 每个事件都会让 `rowViews` 重算（`rows.map` 重建 1000 元素数组 + 1000 次对象展开）；
- `stats` 每次失效要遍历 1000 行、并对每行的 `result.items` 做 `filter` —— 一轮下来扫 12000 张图；
- `completedCount` 又一次 O(n) 遍历；`revealTarget` 依赖每一行的结果；
- `updateRow` 用 `findIndex` 找行（O(n)），`ensureRowFromResult` 用 `some` 再 O(n)；
- 点「开始转换」时行 id 从本地 `local-N` 换成服务端 id → **1000 个行组件整批卸载重挂**
  （顺带把用户展开的明细也收起来了）。

### 改了什么

- **结果直接挂在行上**：`RunRow.result`（`markRaw` 包住，避免把上万条明细变成响应式代理），
  行对象自己就是响应式单元 —— 某一行完成只重渲染那一行。
- `rowViews` 退化成 `rows.value.slice()`（只有增删行才重算）；页脚统计改成 `live` **增量计数器**
  （`file.progress`/`file.finished` 时增量加减，收到最终 `summary` 就直接用服务端的数字）。
- `rowIndex` + `eventIndex` 两张下标表：行 id（本地）与服务端 id 各查各的，`updateRow`/`absorbResult`
  都变成 O(1)。
- `applyStarted` 按路径复用已有行对象（只改字段），组件 key 保持稳定 →
  开始转换时不再整批重挂，展开的明细也不会被收起。
- Go 侧 `FileResult` 新增 `Reused` 字段（`runner.go` 的计数分支拆开，
  `StatusReused`/`StatusCached` 同样算「替换成功」但单独记 `Reused`），
  界面不必再为了显示「复用几张」去数上万条明细。

### 改之后

| 指标 | 改之前 | 改之后 |
| --- | --- | --- |
| settle（点开始 → 界面安定） | 1586 ms | **588 ms** |
| 最长帧间隔 | 489 ms | **162 ms** |
| 超过 100 ms 的帧 | 5 | **2** |
| 一轮收到的 SSE | 4612 | 4054（事件没少，只是不再逐条重算列表） |
| JS 堆峰值 | 60.5 MB | 39.6 MB |

页脚数字与命令行基准逐项一致（1000 个文件 · 12000 张图 · 替换 9837 · 失败 1163），
夹具里 1000 个 `.converted.md` 全部就位。

### 一条走不通的路（记下来别再试）

给行加 `content-visibility: auto` + `contain-intrinsic-size: auto 56px`，想让屏幕外的行
不参与布局绘制 —— 结果 **settle 从 746 ms 劣化到 3126 ms**（最差帧 1.6 s）。
原因是「56px」这个估计值离真实行高（约 90px）差太多，1000 个被 contain 的盒子让每次内容变化
都要重算包含块布局。回滚后恢复原值（同一个构建产物哈希）。要真省，得做虚拟滚动
（只挂可见的十几行），那是另一件事，目前 1000 篇 588 ms 的往返已经够用。

### 顺带记一笔测量口径

用 Playwright/CDP 采 CPU profile 时，**无障碍树的开销被算进来了**（自动化本身会常驻一棵
accessibility tree）：一轮 1.26 s 的 profile 里 `getTextAlternativeInternal` 117 ms、
`getCSSContent` 10 ms、若干 ARIA 计算合计约 145 ms；`(program)` 449 ms（样式/布局/绘制）、
`(idle)` 432 ms、GC 12 ms，而**我们自己的 JS 自耗时合计只有 50 ms 左右**。
真实用户在 WebView2 里跑（没有屏幕阅读器、没有自动化）时，这部分开销会小得多 ——
所以真机手感应当好于上表，上表是「带自动化开销」的偏悲观值。

## 第 8 轮：取消不是失败

按「取消」的时候，第一版实现会把每一个还没处理的文件都标成 `failed`：1000 篇文档、慢图床
（600 ms/张）跑到一半点取消，**1000 行全红**，页脚写着「失败 11000」。三处原因都在
`internal/conv/runner.go`：

1. 派发循环 `for i := range files { work <- i }` 不看 `ctx` —— 取消之后仍然把 1000 个文件
   逐个喂给 worker，每个都白走一遍空转的 `processFile`。
2. `processFile` 结尾把取消的文件写成 `FileFailed`，而它上面的计数 switch 已经把 10 个
   `StatusFailed` 图算进了 `res.Failed`。
3. `uploadGroups` 只要 `uerr != nil` 就把图标成 `failed`，不管这次失败是不是取消引起的。

### 改了什么

- 派发循环加 `if ctx.Err() != nil { break }`：取消之后一个文件都不再派，没轮到的文件保持
  空结果（界面把它们显示成「已取消」，它们确实一个字节都没被碰过）。
- 新增 `StatusCancelled`（图）与 `FileCancelled`（文件）：因取消而没传成的图记
  `StatusCancelled` 并计入 `Skipped`，不计入失败；被取消的文件状态是 `cancelled`，汇总里
  既不算成功也不算失败。
- `uploadGroups` 用 `upload()` 返回的状态，不再把取消一律压成 `failed`；`upload()` 自己在
  请求失败时也区分「取消」与「真的失败」。
- 前端补登记两个状态（`types.ts` 的联合类型、`FileRow.vue` 的 `FILE_STATUS_META` /
  `IMAGE_STATUS_META`）——服务端发一个前端没登记的状态，行状态会直接渲染不出来。

### 复测（1000 篇 / 12000 张图，假图床 600 ms/张，跑到 250 ms 时点取消）

| 指标 | 改之前 | 改之后 |
| --- | --- | --- |
| 取消 → 界面安定 | 280 ms | **135 ms** |
| 行状态 | 失败 ×1000 | **已取消 ×1000** |
| 页脚 | 替换 0 · 失败 11000 · 已取消 | **替换 0 · 失败 18 · 已取消** |
| 一轮推的事件 | 5025 条（`file.started` / `file.finished` 各 1000） | **105 条**（只碰了 17 个文件） |
| 落盘的输出 | 0 个 | 0 个（也没有残留的临时文件） |

那 18 个失败是**真的缺图**：夹具里每篇文档都故意放了一个不存在的 `images/missing.png`，
被碰过的文件如实报出来；剩下的 980 多个文件一个字节都没动。

回归钉在 `internal/conv/runner_test.go` 的 `TestCancelIsNotFailure`：第一次上传时就把 ctx
取消掉，断言汇总不标失败、被取消的文件不写输出、没轮到的文件结果为空、目录里 0 个
`.converted*`。

## 第 10 轮：5000 篇也不卡（文件级事件按文件合并 + 列表虚拟化）

第 7 轮把 1000 篇的界面往返从 1.6 s 压到 0.6 s，这一轮把语料加到 **5000 篇 / 60000 张图**
（`%TEMP%\cmp-gui-5000`，13.94 MB），一上来就撞出两个新的浏览器侧缺陷：

1. **行状态大面积撒谎**。页脚数字是对的（它来自 `run.finished` 的 summary），但
   `rowStatusCounts` 是 `{ 部分失败: 3343, 上传中: 16, 待转换: 1641 }` —— 1657 行永远停在
   「待转换 / 上传中」。根因是服务端订阅者队列 `subscriberQueueLimit = 4096`：5000 篇会产生
   10000+ 条**文件级**事件，队列灌满后按「丢最旧的普通事件」处理，而 `file.started` /
   `file.finished` 对界面来说就是结果本身，不是可有可无的噪声。那次浏览器只收到
   `file.finished` 3343 条。
2. **5.7 秒的单帧停顿**。5000 行 FileRow（每行 91.75 px）全挂在 DOM 里，任何一批事件都要
   patch 5000 个组件 + 浏览器重排/重绘整张 45.8 万像素的表。实测最差帧
   `[5702, 1675, 395, 332, 258, 224] ms`，>100 ms 的帧 11 个。

改法（两侧一起）：

- **服务端**：`file.started` / `file.progress` / `file.finished` 不再各自排队，而是共用
  「每个文件一个槽」的表，只留最新一条；槽攒到 `subscriberSlotBatch = 256` 条、或遇到
  run 级事件时，按首次出现顺序落进下发队列。这样事件总量从 ~10000 降到 ≤ 文件数，
  **每个文件的最终结果都不会被丢掉**。SSE 写出循环在没有终止事件时最多再等
  `sseFlushWindow = 40 ms` 攒一批，一批一次写、一次 flush。
- **前端**：事件按 `EVENT_FLUSH_MAX = 200` 条分片应用（不再一个 tick 里更新上千个组件）；
  文件列表**虚拟化**——只挂可视区上下各多 4 行的 FileRow，前后用占位块撑起滚动高度，
  行高实测（`ResizeObserver` + `data-row-id`）修正偏移表，滚动时二分定位。
- **兼容**：合并会改变事件的到达顺序，`file.finished` 找不到对应 id 时按 pathKey 认领已有
  的本地行，避免造出重复行。

5000 篇 / 60000 张图，假图床 5 ms/张，输出先删、上传缓存热（打包版 exe，Playwright 实测）：

| 指标 | 改之前 | 只改服务端 | 加虚拟化 | 再加 40 ms 攒批 |
| --- | --- | --- | --- | --- |
| 入队 5000 行 | 990 ms | 999 ms | 74 ms | **73 ms** |
| 一轮 settle | 9539 ms | 10759 ms | 2064 ms | **1873 ms** |
| 最差帧间隔 | 5702 ms | 4406 ms | 70 ms | **55 ms** |
| > 100 ms 的帧 | 11 | 22 | 0 | **0** |
| 浏览器收到的事件 | ~10600（且不完整） | 6647 | 20561 | **5625**（finished 5000 条全到） |
| 状态没更新的行 | 1657 | 0 | 0 | **0** |
| JS 堆峰值 | 106 MB | 273 MB | 33 MB | **28.6 MB** |
| DOM 里的行 | 5000 | 5000 | 11 | **11** |

1000 篇回归（同一台机器，同一探针）：settle **588 → 454 ms**、最差帧 **162 → 18 ms**、
SSE 事件 **4054 → 1130 条**、JS 堆 **39.6 → 11.9 MB**。

功能核对：页脚与命令行逐位一致（5000 个文件 · 60000 张图 · 替换 49200 · 复用 59 · 失败 5800）、
夹具里 5000 个 `.converted.md` 全部就位、`*.tmp*` 为 0、滚到底部随机抽看的行状态也都是
「部分失败」（探针会滚到底再数一遍，不能只信页脚）、抽检的 `doc-0000.converted.md` 替换正确。

回归钉在 `internal/server/hub_test.go`（客户端全程不读时每个文件的 finished 一个不少、
5000 文件 × 14 条事件合并后总数 ≤ 文件数+1、攒满 256 条就下发、同一文件只留最新状态、
跨批时进度仍排在自己的 finished 前面）。探针 `tools/perf/gui-scale.mjs` 与
`tools/perf/gui-1000.mjs` 一起进仓库，可复现上面两张表。

**测量方法的一个坑（值得记下来）**：`page.fill()` 往 textarea 灌 15 万个字符要 24.6 秒，
而且是平方级的（1000 行约 1 秒、5000 行 24.6 秒）——那是 Playwright 自己的开销，不是应用。
改成 `page.evaluate` 里直接赋值 + 派发 `input` 事件后 `fillMs = 1 ms`。第 7 轮记的
「入队+预览 1214 ms」也主要是这个开销。

## 第 11 轮：图床连不上就别干等

这一轮先做了四组「本来担心有问题」的实测，三组是负结果（行为正确，不需要改），
第四组撞上一个真问题。数字都在下面。

### 负结果：这些地方本来是好的

| 场景 | 实测 |
| --- | --- |
| GBK / UTF-16LE 文档 | `[失败] 文件不是 UTF-8 编码，暂不支持`，源文件一字未动、不留输出、不串码 |
| UTF-8（无 BOM）与 UTF-8（带 BOM） | 正常处理，带 BOM 的输出的 BOM **仍在**（前 3 字节 EF BB BF） |
| 80 字符深目录 + 60 字中文文件名 | 1 张图替换成功，接近 260 字符路径上限也没问题 |
| 单篇 5 MB 文档（6452 行 / 1250 处引用） | CLI **92 ms**、峰值工作集 **40.7 MB**；界面预览 12 ms、展开后行高 43 699 px、8735 个 DOM 节点，最差帧只有 52 ms |
| 空闲 30 秒 | CPU **0 ms**、工作集 56.6 MB、句柄 552，全程不变 |
| 1000 篇连跑 8 轮 | JS 堆稳定在 8.7 MB、DOM 节点 374、`EventSource` 始终 1 个（没有监听器泄漏） |

### 真问题：图床整体不可用时会干等几分钟

用户自建的存储（PicGo 里配的图床）某天不可达：PicGo 进程本身 200 正常响应，
但它把上传转发出去时 `ETIMEDOUT`。20 篇文档 / 59 张 300 KB 图的实测：

| | 改之前 | 改之后 |
| --- | --- | --- |
| 总耗时 | **259.5 s** | **64.9 s** |
| 失败图片数 | 320 处 | 81 处 |
| 用户看到 | 一张张慢慢失败，最后一片红 | `错误：连续 12 张图片上传失败（期间没有一张成功），已停止本次运行——图床多半连不上：http://127.0.0.1:36677` |

改法（`internal/conv/runner.go`）：连续失败计数 + 「这一轮成功过就不再触发」。
阈值定在 **12**：并发默认 16，一次批量请求本来就会同时压十几张图，
阈值太小时网络偶发抖动会误杀整轮；太大时用户又要多等好几轮超时。
触发后用运行自己的 cancel 把整轮掐掉，取消事件里带上汇总与原因，
界面弹红条、命令行打 `错误：…`，两边都能说出「为什么停了」。

顺带修的两处：

* 取消事件原来**不带汇总**，界面和命令行都没法说清原因（现在带上）。
* 命令行把每个文件的失败明细全打出来——5 MB 那篇文档同一张缺图被引用 100 次就是 100 行。
  现在每个文件最多列 20 条，多出来的折成一行 `……另有 N 处问题`。

## 第 12 轮：引用式图片终于能换了（补功能缺口，不是提速）

这一轮先量了命令行的 5000 篇端到端（假图床每次 5 ms）：

| 输出方式 | 墙钟 |
| --- | --- |
| 重定向到 NUL | 1680 ms |
| 重定向到文件（日志 1.96 MB） | 1679 ms |
| `--quiet`（只打汇总） | 1624 ms |

明细全打出来也只多花约 56 ms —— **输出不是瓶颈**，时间仍然花在建 5000 个文件上（与系统/杀毒实时防护串行，已到地板）。
所以这一轮不追速度，去补一个真实的功能缺口。

### 问题

引用式图片 `![alt][label]`（定义 `[label]: images/a.png` 写在文档别处）以前只提示
「本工具暂不处理」，于是整篇文档**一张图都不会被替换**。Typora、Obsidian 导出以及不少
README 都用这种写法，等于这些文档用不了这个工具。

### 改法

新增 `internal/mdscan/refs.go`：解析文档里的链接定义，并把三种引用式写法都认下来。

| 写法 | 替换区间 | 替换后 |
| --- | --- | --- |
| `![alt][label]` | `[label]` 那一段 | `![alt](地址)` |
| `![alt][]`（折叠） | `[]` 那一段 | `![alt](地址)` |
| `![alt]`（简写） | `]` 之后的插入点 | `![alt](地址)` |

* 标签比较忽略大小写、内部空白折叠；同一标签**以第一次定义为准**。
* 代码块/行内代码/注释里的「定义」不算数；`![alt](…)` 行内写法优先。
* 标签在文档里找不到定义时才提示（文案也改成说清楚这件事），否则不打扰。
* 地址里含空格或括号时，替换文本会包成尖括号，避免被当成「地址 + 标题」。
* 文档里的定义行**原样保留**（用户可能还有别的工具依赖它们）。
* 定义表**按需收集**：文档里没有引用式图片时，一个字节都不多扫。

### 数字

* 纯解析（300 篇 / 2.8 MB）：**306 / 314 / 304 MB/s、14700 allocs** —— 与第 9 轮（304/301/296）一致，
  没有回归（不用引用式写法的文档走的是同一条老路径）。
* 引用式压力夹具（85 KB、**2000 处引用式引用、5 张定义图**）：**46 ms**，2000 处全部就地内联化，
  残留引用式 0 处，5 条定义全部保留 —— 5 张图只上传了一次（去重照常生效）。
* `%TEMP%\cmp-paths` 夹具：doc-b 从「3 张成功」变「4 张成功，2 张失败」，整轮替换 14 → 17 处。

### 测试

* `internal/mdscan/scan_test.go`：`TestReferenceStyleResolves`（9 个用例：完整/折叠/简写/大小写/
  空白折叠/尖括号地址带标题/远程地址/没有定义只提示/代码块里的定义不算）、
  `TestReferenceStyleApplyMakesInline`（替换后是等价的整行写法）。
* `internal/conv/runner_test.go`：`TestReferenceStyleImagesAreConverted`（一篇文档里三种写法 +
  一个没有定义的标签，断言三处都换、定义行保留、没定义的那处不动）。

## 第 13 轮：`<pre>` / `<code>` 里的内容不再被误当图片

### 问题

围栏代码块、行内代码、HTML 注释早就跳过，但 `<pre>…</pre>`、`<code>…</code>` 之间的
内容没有跳过 —— 手写 HTML 的文档里，代码示例中的 `![x](img/c4.png)` 会被真的替换掉，
把示例改坏了（还顺手多传一张图）。实测：

```
<pre>
![四](img/c4.png)     ← 改之前会变成 https://…，改之后原样保留
</pre>
```

### 改法

`protectedMask` 增加一段：把 `<pre>`/`<code>` 到对应闭合标签之间的字节全部标记为受保护。
标签名大小写不敏感，且只认真正的标签边界（`<prefix>` 不会被误当成 `<pre>`）；
没有闭合标签时不标记，行为与从前一致。

### 性能（差点写坏）

第一版写成「逐字节扫全文，遇到 `<` 再比较」，两遍扫下来解析从 306 MB/s 掉到 247 MB/s（−20%）。
改用 `bytes.IndexByte(src[i:], '<')` 直接跳到下一个 `<` 之后回到 **299 / 303 / 310 MB/s、
14700 allocs**，与第 12 轮持平。教训：在解析热路径上，即使只是「顺带扫一遍」也要用
`IndexByte`/`Index` 这类 SIMD 跳转，别逐字节走。

### 测试

`TestScanMarkdown` 新增 4 个用例：`<pre>` 内忽略、`<code>` 内忽略、`<PRE>` 大小写、
`<prefix>` 不算 `<pre>`（仍然识别其中的图片）。

## 第 14 轮：文件系统边角上的说法（只读目标、输出目录是文件）

这一轮没有提速目标，去翻「文件系统边角」这一摊，看失败时到底跟用户说了什么。

### 负结果（本来就是对的）

| 场景 | 结果 |
| --- | --- |
| 路径总长 2834 字符（远超 260） | 正常转换（Go 的 os 包会自己加 `\\?\` 前缀） |
| `-o directory --out-dir <多级不存在>` | 正常创建并写出（目录模式保留原文件名） |
| 图床地址连不上（TCP 层） | 开跑前就拦下：2.2 秒报「无法连接 PicGo：端口未响应（地址）」，不会一张张干等 |
| `<img>` 各种写法（单引号/无引号/大写/`src=` 带空格/自闭合/属性在前） | 全部正确识别 |

### 改掉的两处

**1. 目标文件只读时，甩的是 Go 的原始错误**

改之前：`写入失败：rename C:\…\.cmp-3181963446.tmp C:\…\d1.converted.md: Access is denied.`
—— 临时文件名 + 英文系统调用信息，用户不知道该怎么办。

改之后：`目标文件是只读的，覆盖不了：C:\…\d1.converted.md（去掉只读属性后重试，或换个输出位置）`

实现：`writeAtomic` 里 `os.Rename` 失败后看一眼目标是否存在且没有写权限位，
返回一个 `errTargetReadOnly` 哨兵错误，由 `processFile` 换成上面这句人话（其它写入错误照旧带原始信息）。
原地模式同理：只读的源文件不会被硬闯。

**2. 「输出目录是一个文件」的报错重复两遍、还误导**

改之前：`无法创建输出目录：mkdir …\notadir: The system cannot find the path specified.: mkdir …\notadir: The system cannot find the path specified.`
（文案里嵌了 `%v`，外面又 `%w` 包了一次；而且 Windows 对「同名文件挡路」只会说「找不到路径」。）

改之后：`输出目录是一个文件，不是目录：C:\…\notadir`

顺带把这类「输出位置」问题搬进预检：`planOutput` 的错误以前在试运行里被丢掉
（`if p, perr := ...; perr == nil`），现在会写进预检结果的 `error`，
于是界面在按下「开始转换」之前就能告诉你位置选错了（中英双语都验过）。

### 测试

* `TestPreviewSurfacesBadOutputDir`：输出目录位置上是个文件时，预检必须带 `error`、且不给假输出路径。
* `TestReadOnlyTargetExplainsItself`（限 Windows）：只读目标要给出含「只读」字样的说明，而不是 rename 原文。

### 输出命名：同样一批文件，两次跑出来的名字会换人（真 bug）

`-o directory` 模式下不同目录里的同名文件（`a/post.md`、`b/post.md`）会自动加序号，
但序号是**在各自的工作协程里当场抢的**：`uniquePath` 只查「这一轮已经占用的名字」，
不看输入顺序，也不看磁盘上原来有什么。实测同一个命令连跑 6 次：

```
第 1 次：a → post.md   ；b → post-2.md
第 2 次：a → post-2.md ；b → post.md
第 4 次：a → post-2.md ；b → post.md
第 5 次：a → post.md   ；b → post-2.md
```

两个后果：① 同一批文档两次导出的**文件名会互相串**（上次编辑的 `post-2.md` 这次是另一篇），
版本管理里看着像整批改名；② **预检显示的输出路径未必是真的**——预检和真跑是两次独立的规划，
各抢各的名字。

改法：开工前按**输入顺序**把这一轮所有输出路径一次定好（`planOutputs` → `reserveOutput` 查计划），
预检和真跑走同一份规划。实测：

* 30 个同名文件，连续 6 次真跑，`a → post.md`、`b → post-2.md` … 每次都一样；
* HTTP 预检给出的 30 个名字与随后 `/api/run` 真正写出的 30 个文件**完全一致**。

### 测试

* `TestOutputNamesAreDeterministic`：12 个同名文件，预检两次 + 真跑两遍，输出路径都必须按输入顺序
  （临时把预计划那一行去掉，这条用例立刻失败——它确实在守着这个 bug）。
* 目录文案与 `KeyConvPathIsDir` 走的是既有的端到端用例与人工核对。

## 第 19 轮：两处「用户改不动、也看不见」的边角

这一轮不是提速，是把两个安静的坏行为说清楚。

### 一、设置文件坏了，用户一点都不知道

第 3 轮修过「设置文件带 BOM 就被当成解析失败」的 bug，但**解析失败本身的处理**没动过：
`Load()` 直接 `return Default()`，于是用户手改过 `settings.json`（少个引号、多个逗号）之后，
自己设的图床地址、并发数会**凭空变回默认值**，界面上没有任何提示——他只会觉得「这软件记不住设置」。

现在：读不出来时把原文件另存为 `settings.json.broken`（已存在就不覆盖，第一份才最接近「本来
长什么样」），并把这件事说给用户听：

| 出口 | 说法 |
| --- | --- |
| 图形界面 | 「关于」里一条红色提示：`设置文件读不出来（不是合法的 JSON），已改用默认值。 原文件另存为 …settings.json.broken，改好它可以恢复设置。` |
| `/api/health` | 新增 `settingsNote` 字段（英文请求返回英文） |
| 命令行 | 开头一行 `提示：设置文件读不出来…`（在 `Load()` 之后打印——Load 才是发现问题的动作） |
| 磁盘 | 原文件被复制成 `settings.json.broken`，改好它就能恢复设置 |

实测（`CMP_DATA_DIR` 指向一个装着 `{ this is not json` 的目录）：CLI 打印上面那句提示、
`.broken` 里是原始字节、`/api/health` 的 `settingsNote` 中英各自正确、改回合法 JSON 后提示消失。

### 二、两个 `/api/run` 会各自开一个 Runner

`handleRun` 原来只管把 `cancel` 记进 `s.runs`、起一个 goroutine，**没有「已经在跑」的判断**。
界面因为 `busy` 挡住按钮，正常点不出来；但 `/api/run` 是文档里公开的接口，脚本连发两次、或者
两个窗口一起点，就会有两个 Runner 同时处理同一批文件：同一张图被传两遍、同一份输出被两边
反复写（原子写保证不写坏，但结果与统计会互相打架），而界面只有一套进度可显示。

现在同一时刻只允许一次：第二次请求返回 `409`，错误码 `conflict`，消息「已经有一次转换在跑，
等它结束或先取消再试」。`codeFor` 里补了 409 → `conflict`（原来落到默认的 `error`）。

回归测试两条：`internal/settings` 的 `TestStoreReportsBrokenFile`（坏文件 → 默认值 + 提示 +
`.broken` 字节一致 + 第二次读取仍指出位置 + 改好后提示消失 + 英文提示不含中文）、
`internal/server` 的 `TestRunRejectsConcurrentRun`（图床卡住不返回时，第二次 `/api/run` 得到 409
且带 `conflict` 消息）。实测也各跑了一遍：`/api/health` 给出 `settingsNote`，慢图床下第二次
`/api/run` 得到 `HTTP 409`。
## 第 20 轮：文件被别的程序占着时，别再打印系统原话

顺着第 14 轮「失败说法」那条线继续往下查，这次盯的是**文件被占用**——真实场景很常见：
用户把 `.converted.md` 开着看、或者在 Typora / Word 里开着源文档，又点了一次转换。实测两种：

| 情况 | 改之前的说法 |
| --- | --- |
| 输出文件被占着（生成副本模式） | `写入失败：rename …\.cmp-2853839841.tmp …\a.converted.md: Access is denied.` |
| 源文件被占着（原地模式） | `无法读取文件：open …\b.md: The process cannot access the file because it is being used by another process.` |

第一句尤其糟：它把**随机命名的临时文件**摆到用户面前，还只说「Access is denied」——
用户根本不知道是谁在拒绝什么。两句现在都换成了：

```
[失败]  a.md   写不进去：文件正被别的程序占用，或者没有权限：…\a.converted.md（关掉占用它的程序再试）
[失败]  b.md   读不出来：文件正被别的程序占用，或者没有读取权限：…\b.md（关掉占用它的程序再试）
```

### 一个 Go 的坑：共享冲突不在 fs.ErrPermission 里

写不进去那条容易修：`writeAtomic` 的 rename 失败后已经会 stat 目标，加一条
`errors.Is(err, fs.ErrPermission)` 就够了。但**读**那条光靠 `fs.ErrPermission` 抓不到——
Windows 给的是 `ERROR_SHARING_VIOLATION(32)`，而 Go 的 `syscall.Errno.Is` 只把
`ERROR_ACCESS_DENIED(5)` 映射到 `fs.ErrPermission`。实测（直接构造 Errno）：

```
Errno(5)  -> fs.ErrPermission=true    # Access is denied
Errno(32) -> fs.ErrPermission=false   # 文件被别的程序占着
Errno(33) -> fs.ErrPermission=false   # 区域被锁
```

所以新增了 `platform.IsBusy(err)`：Windows 上认 5 / 32 / 33，其它平台就是权限错误。
（`syscall` 包没给这两个常量，`golang.org/x/sys/windows` 里有，但 `internal/platform`
一直坚持「不引 cgo、不引第三方库」，所以按数值定义并用注释标明出处。）

### 回归测试

`internal/conv/runner_windows_test.go`（新增，`//go:build windows`）两条用例：用
`syscall.CreateFile(..., dwShareMode=0, ...)` 把文件锁住（`os.OpenFile` 不行，Go 默认
允许共享读写删除），再跑一轮，断言错误文案里有「占用」且**不含 `.tmp`**。
把 `platform.IsBusy` 换回 `errors.Is(err, fs.ErrPermission)` 之后 `TestLockedSourceExplainsItself`
立刻失败，说明它确实守着这个修复，不是空跑。

顺带复核：只读目标仍然走第 14 轮那句「目标文件是只读的，覆盖不了」；内容没变时
「跳过写入」的快路径也仍然不报错（只读目标只有在新内容确实不同时才会被写）。
## 第 21 轮：更新完之后，界面不再停在「正在重启」

前 20 轮量的都是转换链路，这一轮把「更新」这条路径从头到尾在界面上演练了一遍
（第 16 轮只演练了 API）。

演练环境：`%TEMP%\cmp-fileserver.exe` 在 36681 上服务清单 `version.json`（9.9.9，
sha `4998381a315e…`，size 14,367,744）和 `candidate.exe`（用
`-ldflags "-X …/internal/version.Version=9.9.9-test"` 编出来的假新版本）；
把当前 exe 复制到 `%TEMP%\cmp-update-gui\`，带
`CMP_UPDATE_MANIFEST=http://127.0.0.1:36681/version.json` 在 17998 上跑。
探针：`tmp-update3.mjs`（仓库外的一次性脚本，思路在下面）。

### 第一次演练：装是装上了，页面不动

状态走得很顺：`有新版本可以更新` → `正在下载 0%` → `正在重启，界面马上会重新打开`，
3 秒后同一个端口 17998 的 `/api/health` 已经报 `9.9.9-test`，exe 也换成了
14,367,744 字节 —— **但浏览器里那一页永远停在「正在重启」**。
原因：`useUpdate` 的轮询在重启期间请求失败就静默停了，谁也没告诉页面「新版本已经起来了」。

### 改法

`install()` 记下装之前的版本号，然后 `waitForRestart()` 每 700 ms 问一次
`/api/health`，**只在版本号真的变了的时候** `window.location.reload()`
（最多等 90 秒）。只认「版本变了」这一个信号，是因为重启中途端口会短暂不可用，
而旧进程也可能还在应答同一个版本 —— 这两种都不该触发刷新。

### 第二个坑：拿两个格式不同的版本号直接比字符串

第一版写的是 `health.version !== wasVersion`。实测**页面 312 ms 就刷新了，刷完还是 v1.0.0**：

* 界面上的 `current` 是 `v1.0.0`（短格式，底栏就显示这个）
* `/api/health` 报的是 `1.0.0 (4cc55e4)`（带提交号）

两个字符串永远不相等，于是页面在**旧进程还占着端口**的时候就刷新了一次，
刷回来当然还是旧界面。改成先取出数字部分再比（`versionCore()`）之后：

| | 直接比字符串 | 取数字部分再比 |
| --- | --- | --- |
| 刷新时刻 | 点完 312 ms（旧进程还活着） | 点完 934 ms（新进程已接管） |
| 刷新后页脚 | `v1.0.0`（还是旧的） | **`v9.9.9-test`** |
| exe | 14,367,744 字节 | 14,367,744 字节 |

两次演练的完整状态流都是 `有新版本可以更新` → `正在下载 0%` →
`正在重启，新版本起来后界面会自动刷新`，区别只在刷新后看到的是哪个版本。

### 顺带确认的

* 桌面窗口形态不受影响：旧进程退出、新进程开新窗口，页面刷不刷新都无所谓。
* 更新期间「关于」弹窗里的按钮是锁住的（`locked`），下载百分比会走。
* 演练用的 exe 是复制的副本，所以整个演练不碰仓库里的 `bin\convert-md-picture.exe`。
## 第 22 轮：图床限流（429 / 503）不再被当成「图床挂了」

前几轮把"图床整个连不上"和"文件被占用"都照顾到了，但漏了一类很常见的情况：
图床**活着**，只是回答 429（请求太频繁）或 503（暂时不可用）。
原来的代码里，只有 `>= 500` 才算「可重试」，其余非 200 一律直接判死：

```go
if resp.StatusCode >= 500 {
    return "", true, ...   // 重试
}
if resp.StatusCode != http.StatusOK {
    return "", false, ...  // 直接失败（429 走的就是这条）
}
```

于是 429 立刻变成一张图的失败。更糟的是它会喂给第 11 轮那个熔断器：
连续 12 张失败 + 整轮没成功 ⇒ 掐掉整轮，并报「图床多半连不上」——
**而图床明明是通的，还在好好回 JSON**，这句话会把用户带向完全错误的排查方向。

### 改法

1. **429 / 503 可以重试**，并且读 `Retry-After`（秒数或 HTTP 日期都认）。
   解析不出来就自己退避 1 秒；单次最多等 10 秒（再长就不礼貌了，用户可以随时取消）。
2. **冷却闸门是全体共享的**：一个协程被限流，其它 15 个也不会继续撞上去——
   都是同一个 `Client`，把「可以再发了」的时刻记在客户端上（`gateUntil`），
   每个请求发出去之前先过一道 `waitTurn`。没有冷却时这一步几乎不花时间。
3. **限流有自己的重试预算**（5 次），不复用普通失败的 2 次：
   图床是活的，多等两轮很正常。
4. **限流不再算进「图床挂了」的熔断**。另起一条线（`limitStreak`），
   一直限流时给的是另一句话：

   > 图床一直回「请求太频繁」（连续 12 张没成），已停止本次运行——它是通的，过一会儿再试，或把并发调小：<地址>

### 实测（`bin\convert-md-picture.exe`，假图床 `tools/mockpicgo`）

给假图床加了 `-ratelimit <n>`（前 n 次请求回 429）和 `-retry-after <时长>`，
用四个不同端口的实例做前后对照，夹具是 6 篇 / 13 篇各带一张图的文档。

**场景 A：偶发限流**（前 3 次请求 429，6 篇文档）

| | 改之前 | 改之后 |
| --- | --- | --- |
| 替换链接 | 3 处 | **6 处** |
| 失败 | 3 处 | **0** |
| 真正写出来的文件 | **3 个**（另外 3 篇「所有本地图片都处理失败，未生成文件」） | **6 个** |
| 用时 | 0.0 s | 1.0 s |

一次限流就让一半文档彻底没生成；改完之后这 3 次限流被重试救回来，`doc-00.md` 里已经是
`![x](https://mock.local/doc-00.png)`。

**场景 B：一直限流**（前 100 次请求 429，13 篇文档）

| | 改之前 | 改之后 |
| --- | --- | --- |
| 用时 | 0.0 s | 4.0 s（每一轮都按 Retry-After 等了） |
| 结果 | 失败 11 个 · 已取消 | 失败 8 个 · 已取消 |
| 说法 | 「…已停止本次运行——**图床多半连不上**：<地址>」 | 「…已停止本次运行——**它是通的**，过一会儿再试，或把并发调小：<地址>」 |

两边的耗时都不到一眨眼是因为熔断器（12 张）很快就到了；区别在于改完之后它先认真重试、
再给一句能照着做的结论。

### 回归测试

`internal/picgo/picgo_test.go`：429 会重试而不是判死（`TestUploadRetriesWhenRateLimited`）、
503 同样重试、`Retry-After: 1` 真的等满 1 秒（`TestUploadHonorsRetryAfterSeconds`）、
一直限流时试满限流预算才报错、冷却闸门挡住其它上传（`TestCooldownGateBlocksOtherUploads`）、
取消时 `waitTurn` 立刻返回、`parseRetryAfter` 的八种输入（含秒数、HTTP 日期、过期日期、垃圾值）。

`internal/conv/runner_test.go`：一直限流时给的是「请求太频繁」而**不是**「连不上」
（`TestAbortsWhenEndpointRateLimits`）、偶发限流（前 3 次 429）该被重试救回来一张不失败
（`TestRateLimitBurstIsRetriedNotFailed`）。

反证过：把 429/503 那个分支改成 `if false`，`TestUploadRetriesWhenRateLimited` 立刻失败，
报的正是老行为「PicGo 返回 429: slow down」。这两个用例的等待时间加起来约 8 秒
（限流重试就是要等），所以 conv 包的测试从 1.5 秒变成 9.6 秒——值得。

## 第 24 轮：fuzz 抓到「一个畸形标签让整个程序卡死」

### 为什么这轮换成 fuzz

前 23 轮都是手写边界用例（编码、路径、后缀、代码块、标签、文件被占用、图床限流…）。
手写用例只能覆盖「想得到的」输入；这一轮换一种找法：给扫描器写一个 fuzz 目标，
让机器去撞「想不到的」输入，断言它在任何字节串上都不会 panic、不会卡住，
而且给出的引用区间自洽。

`internal/mdscan/fuzz_test.go` 的 `FuzzScanLang`：20 条种子（正常写法、引用式、
尖括号、代码块、`<pre>`、注释、BOM+CRLF、畸形截断），每次断言两件事：

- 每个引用都满足 `Start <= URLStart <= URLEnd <= End <= len(src)`；
- 用各引用自己的 URL 区间 `Apply` 一次不报错，并且结果长度等于
  `len(src) - 被替换的字节数 + 13 * 引用数`（`13` 是替换文本 `https://mock.local` 的长度）。

### 69 秒时挂住了

`go test ./internal/mdscan/ -run FuzzScanLang -fuzz FuzzScanLang -fuzztime 90s`：
跑到第 69 秒，execs 从约 80 万/秒掉到 **0** —— 整个 fuzz 进程卡死不动，只能 Ctrl+C。
失败输入被写进 `internal/mdscan/testdata/fuzz/FuzzScanLang/4b4cebd9feeaa7ac`
（1058 字节，开头是 `<img "0000…`）。

定位方式是临时测试里把 `ScanLang` 放进 goroutine，再
`pprof.Lookup("goroutine").WriteTo(os.Stdout, 1)` 打全部栈：卡在
**`parseHTMLImage`（`internal/mdscan/scan.go:361`）**的属性循环里原地打转。

### 根因：一个可以「零进展」的 continue

属性循环的骨架是这样的：

```go
for i < tagEnd {
    nameStart := i
    for i < tagEnd && !isSpace(src[i]) && src[i] != '=' && src[i] != '>' {
        i++
    }
    if i == nameStart {
        // 站在 '=' 或 '>' 上：这里不是属性名
        if src[i] != '=' {
            i++
            continue
        }
    }
    ...
    if i >= k || src[i] != '=' {
        continue      // ← 回到循环开头，位置一点没动
    }
```

当 `src[i]` 是 `=` 或 `>` 时，名字扫描一格都不动（`i == nameStart`），
随后那条 `continue` 也回到同一个位置 —— **死循环**。

能不能走到 `>` 上，取决于 `tagEnd`（取标签里最后一个 `>`）与属性解析各自
怎么对待引号：畸形引号会让两者错位。最小复现：

```html
<img "a b>c" x>
```

同一批候选里 `<img = = >`、`<img alt=x >`、`<img alt="a>b" >`、`<img src="a.png" >`
都不卡（属性名非空，或者一碰到 `src` 就返回了），所以这个洞藏得很深。

### 影响面：不用恶意构造，编辑器里打错一个引号就行

`ScanLang` 在三条路径上都会被调用：命令行、`/api/preview`、`/api/run`。
也就是说，文档里出现这么一行，命令行会**永远挂着不返回**（用户只能去杀进程），
服务端的预检请求也永远不结束 —— 界面表现为「点了预览/开始转换，一直转」。

### 修法

给循环补上「一定往前走」的保证：

```go
		if i == nameStart {
			// 站在 '=' 或 '>' 上，说明这里根本不是属性名。畸形标签里很常见
			// （属性名位置上来个引号，引号里又有个 '>'，tagEnd 就会落在它后面），
			// 往前挪一格保证循环一定往前走 —— 以前这里会原地死循环，
			// 一个畸形标签就能让整个程序卡死（fuzz 抓到过）。
			i++
			continue
		}
```

顺手把 `internal/mdscan` 里所有带 `continue` 的循环都过了一遍：`scan.go` 的
75/107/482/539 行外层都在 `continue` 前自增，132/179/212 行与 `refs.go` 的内层
同样自增，`looseDestEnd` 用的是 `for` 语句自增形式 —— 只有属性循环这一处零进展。

### 回归测试

`internal/mdscan/hang_test.go`：

- `TestScanNeverHangsOnBrokenHTML`：17 条畸形 `<img>` 写法（含最小复现、
  `<img = = >`、`<img "` 等），每条给 1 秒时限；正常扫描是微秒级。
- `TestScanFuzzCorpus`：把 `testdata/fuzz/FuzzScanLang/` 下的语料当固定用例跑一遍，
  这样 fuzz 抓到的东西在普通的 `go test` 里也会被守住。

一个自己踩的坑：`scanWithin` 辅助函数**必须**把 `ScanLang` 放进 goroutine 里跑，
否则主测试协程自己就卡在里面，根本没机会走到超时分支（第一版就是这么写的，
测试挂了两分钟才被 `-timeout` 杀掉）。

### 验证

  **8 秒不返回 → 强杀**。

- `go test ./internal/mdscan/ -count=1` 0.9 秒全绿（含 fuzz 语料回归）。
- 修复后再 fuzz 5 分钟：**178,756,995 次执行、0 失败**（`PASS`，302 秒）。

### 顺带补的 i18n 审计

`internal/i18n` 此前一条测试都没有。补了 `i18n_test.go`：

- `TestCatalogIsComplete`：每条键的中英文都非空、文案不能正好等于键名、

## 第 25 轮：把 fuzz 铺到其他「吃外部字符串」的函数上

第 24 轮那次死循环说明一件事：**索引型解析器最怕的不是「算错」，而是「不动」**。
这一轮把同一套找法（给函数写性质、让机器去撞）铺到了另外两个吃外部输入的地方：
版本号比较（输入来自网络上的版本清单）和 `Retry-After` 解析（输入来自图床响应头）。

### 版本号比较：1 270 万次执行，没找到问题

`internal/update/fuzz_test.go` 的 `FuzzCompare` 断言三条性质：结果只能是 -1/0/1、
自己和自己比必须是 0、反对称（`Compare(a,b)` 与 `Compare(b,a)` 符号相反）。
种子覆盖了空串、`..`、`1..2`、`1.0.0-3-gabc1234`、`9.9.9-test`、`+build.5`、
40 位数字、`一.二`、带换行和 NUL 的版本号等。

跑 60 秒：**12,712,086 次执行，0 失败**。也就是说这套比较逻辑在最脏的输入上
仍然自洽（这条性质很重要：它决定「有没有新版本」，一旦自相矛盾，用户会看到
「有更新」和「已是最新」来回跳）。

### Retry-After 解析：抓到一个真的整数溢出

`internal/picgo/fuzz_test.go` 的 `FuzzParseRetryAfter` 断言：不能 panic、
不能返回负数、纯十进制必须按秒解析（超过上限的按上限）、HTTP 日期要落在
「从现在到那个时刻」附近。

跑起来第一次就失败了：

```
parseRetryAfter("9227000000") = -2561040h1m13.709551616s，不能是负数
```

`9227000000` 秒 ≈ 9.227e18 纳秒，**刚好越过 int64 的天花板（9.223372036854775807e18）**，
`time.Duration(secs) * time.Second` 直接回绕成负数。

现实影响：`uploadOnce` 拿到这个值后有一句 `if wait <= 0 { wait = defaultCooldown }`
兜着，所以线上不会「睡负数」，只是把一个离谱的等待悄悄降级成默认的 1 秒 ——
**行为侥幸正确，值是错的**。而且这个函数是给整个包用的，下一个直接用它的调用点
就会踩到（`cool()` 只处理「太大」，不处理负数）。

修法是给解析加一条上限：

```go
	// maxRetryAfter 是 Retry-After 能接受的等待上限。两个理由：
	// 一是别让超大数字把 int64 撑爆（fuzz 用 "9227000000" 抓到过…）；
	// 二是协议上超过一天的等待本来就没有意义——真要等那么久，
	// 调用方也会把它截到 maxCooldown。
	maxRetryAfter = 24 * time.Hour
```

数字与 HTTP 日期两条路径都按这个上限截断；`TestParseRetryAfter` 补上
`9227000000`、`99999999999`、`86401`、`86400` 四组用例，fuzz 语料也留在了
`testdata/fuzz/FuzzParseRetryAfter/` 里。

顺带被 fuzz 教育了一次测试本身：`Wed, 01 OCt 7000 0:00:00 GMT` 这种「年份 7000」的
日期 Go 的 `http.ParseTime` 是会接受的，`time.Until` 直接顶到 `Duration` 的天花板
（2562047h…），于是断言里那个「与预期差得太多」先炸了 —— 断言也得跟着截断，
否则测的是断言不是实现。

修完再跑 120 秒：**26,021,232 次执行，0 失败**。

## 第 28 轮：文档编码（UTF-16 / 本机 ANSI）从「拒收」变成「支持」

**缺口**：`runner.go` 原来的判断是 `if !utf8.Valid(data) { 失败：「文件不是 UTF-8 编码，暂不支持」 }`。
记事本「Unicode」存出来的 UTF-16、老中文文档的 GBK，整份都被拒收 —— 一个字都没换。

**实现**（新增 `internal/textenc`，不引第三方库、不碰 cgo）：

- `Detect`：`FF FE` → UTF-16LE、`FE FF` → UTF-16BE、其余只要 `utf8.Valid` 就当 UTF-8、否则当本机 ANSI。
  **没有 BOM 的 UTF-16 不猜**（猜错代价太大）。UTF-8 BOM 归到 UTF-8 并当内容原样保留。
- UTF-16 用 `unicode/utf8` 手写码元转换；孤立代理项、奇数长度一律报错，不写替换字符。
- ANSI 走系统 API（`MultiByteToWideChar` / `WideCharToMultiByte`，CP_ACP，中文机器上是 936），
  写回时带 `WC_NO_BEST_FIT_CHARS` + `lpUsedDefaultChar`：**表达不了就报错，不悄悄写 `?`**。
- 安全阀：`Decode` 的 ANSI 分支解出来以后**立刻 `Encode` 回去和原文逐字节比**，不一致就拒收。
  于是「只要读进来了，写回必定逐字节一致」，不会把非 ASCII 部分改坏。
- 接线三处：预扫（不解码的话 UTF-16 文档在界面上永远显示 0 张图）、`processFile` 读入、
  **写回前按原编码再编回去**（UTF-16 的文档不该因为我们处理过就变成 UTF-8）。

**真机验证**（`%TEMP%\cmp-enc` 五个文件：deep / gbk / utf16 / utf8 / utf8bom）：

| 文件 | 改之前 | 改之后 | 输出编码（用 .NET 独立解码核对） |
| --- | --- | --- | --- |
| gbk.md | 失败：不是 UTF-8 | 2 张成功 1 张失败 | GBK，首字节 `23 20 D6 D0 CE C4`（「中文」） |
| utf16.md | 失败：不是 UTF-8 | 2 张成功 1 张失败 | UTF-16LE，`FF FE` 开头 |
| utf8.md / utf8bom.md | 2 张成功 1 张失败 | 同左 | UTF-8 / UTF-8 + BOM（BOM 保留） |
| deep.md（长路径） | 1 张图片 | 同左 | UTF-8 |

「1 张失败」是夹具里故意留的 `img/missing.png`。把原文件的两处地址换成图床地址后与输出**逐字节相等**；
五个源文件的 SHA-256 跑完一个都没变。

**性能：GBK 不比 UTF-8 慢**（`tools/bench`，1000 篇 / 12000 处引用 / 假图床 5 ms / 5 轮）：

| 夹具 | 中位墙钟 | 峰值堆 | totalAlloc |
| --- | --- | --- | --- |
| UTF-8 | 3.222 s | 20.9 MB | 42.9 MB |
| GBK（1000 篇全部转成 GBK） | 3.228 s | 21.8 MB | 81.8 MB |

端到端没有可测差异（0.2%，在噪声内）。多出来的分配是「解码 + 编码 + 逐字节比对」那点垃圾：
1000 篇多 39 MB，平摊每篇 39 KB，GC 完全无感。

**已知局限**（写在 README 里）：没有 BOM 的 UTF-16 认不出来；非本机代码页的老编码
（例如中文机器上的 Shift-JIS）会被当 ANSI 解，可能解出乱码路径 —— 但**绝不会改坏字节**：
要么解出的内容能逐字节写回（那就照常处理，只是路径可能找不到文件），要么直接拒收并提示另存为 UTF-8。

## 第 30 轮：两个「用户按了按钮却没反应/反应过头」的边角

**（一）请求体超过 4 MB 时，报的是「JSON 写坏了」**

`decode` 原来是 `json.NewDecoder(io.LimitReader(r.Body, 4<<20))`：超限的请求体被截成半截 JSON，
解出来是 `unexpected EOF`，于是界面/命令行显示「请求内容格式不对」—— 用户完全看不出是「太多了」。

改成先 `io.ReadAll(io.LimitReader(r.Body, maxRequestBody+1))`（多读一个字节就能分清「刚好到上限」和「超过」），
超限返回 `413` + `error.code = "too_large"` + 「请求内容太大（超过 4 MB），请分成几次提交」。
真机核对（`curl --data-binary`，6.68 MB 的请求体）：

| | 改之前 | 改之后 |
| --- | --- | --- |
| 状态码 | 400 | **413** |
| error.code | `bad_request` | **`too_large`** |
| 文案 | 请求内容不是合法的 JSON | 请求内容太大（超过 4 MB），请分成几次提交 |
| 正常体积（3.78 MB / 6 万条路径） | 200 | 200（不变） |

顺带给 `http.Server` 补了 `ReadTimeout: 60s` / `IdleTimeout: 120s`：只设 `ReadHeaderTimeout` 时，
一个只发头不发体的连接能一直占着协程。只读超时不影响 SSE（那是写方向的长连接）。

**（二）「输出到目录」的输出目录正好是源目录时，悄悄变成原地覆盖**

夹具：一篇 `doc.md` + 一张图，`-o directory --out-dir <源目录>`。

| | 改之前 | 改之后 |
| --- | --- | --- |

| 跑完的结果 | 永远看不到 | 接着往下走，最后「替换 20」、13 行全「完成」 |

**机理**：事件流是增量的。`run.started` 只在 `runId === null && phase === 'preparing'` 时被接受，
而刷新之后前端内存里的 `runId` 是 null、`phase` 是 `idle`，于是整条事件流被 `matches()` 挡掉；
服务端也没有「现在在跑什么」的接口，前端没有任何办法把状态接回来。

**改法（服务端记现状 + 前端连上就问一次）**：
- `internal/server/server.go`：新增 `runSnapshot{runID, files, results, summary, done}` 与 `Server.current`；
  runner 的事件出口包一层 `track(runID)`，按事件类型把 `run.started` 的文件清单、
  每个 `file.finished` 的结果、终止事件的汇总记进快照，然后照常广播。
  新增 `GET /api/run/current` 返回 `{ running, done, runId, files, results, summary }`；
  `done=true` 的那份只回一次（留给「刚刷新完想看上一轮结果」的那一次请求），再问就清掉。
- `web/src/composables/useRun.ts`：新增 `adoptSnapshot()` 与 `resync()`，在 `EventSource.onopen`
  里先问一次现状再接着吃增量（重连同理）。快照里的结果直接 `absorbResult` 到对应的行上，
  还在跑的标成「上传中」，所以刷新后取消按钮、进度、结果都在。
  用模块级的 `lastAdoptedRunId` 挡住「一轮已经结束、重连又把它变回界面」。
- 顺手修掉一个数据竞争：`handleRun` 的后台协程原来在里面调 `langOf(r)`，
  而 `*http.Request` 在 `ServeHTTP` 返回后会被连接复用——改成启动前取好 `lang` 再闭包捕获。

回归测试 `TestCurrentRunSnapshot`：没跑过时 `running=false`；图床卡住时 `running=true`、文件清单到位、
结果为空；放行后同一接口能拿到 `results[0].uploaded == 1` 与 `summary`。
`docs/API.md` 端点表补 `/api/run/current`，README 的图形界面一节补一段「刷新/断线不会丢这一轮」。
## 第 32 轮：「输出到目录」的输出目录建在被扫描目录里面时，产物会被当成输入

**问题**：`-o directory --out-dir docs\out docs` 这种写法很自然（产物不想和原稿混在一起，
就在原稿目录下开个子目录），但 `ExpandPaths` 只按 `*<suffix>.md` 过滤产物，
而目录模式的产物文件名是**原文件名**（`a.md`），于是第二次运行会把 `docs\out\a.md` 当成待处理文档。

实测（夹具 `%TEMP%\cmp-nested`：`docs\a.md` + `docs\img\one.png`，输出到 `docs\out`）：

| 第几遍 | 改之前 | 改之后 |
| --- | --- | --- |
| 第 1 遍 | 1 个文件 · 替换 1 处 | 1 个文件 · 替换 1 处 |
| 第 2 遍 | **2 个文件**：`a.md` 完成 + `a.md`（`docs\out\a.md`）「没有本地图片」 | **1 个文件** · 替换 1 处 · 省下 1 张重传 |
| 第 3 遍（`--dry-run`） | **2 个文件**：1 处待上传 + 1 处网络图片（把产物又数了一遍） | **1 个文件** · 1 处引用 · 1 处待上传 |

界面上的表现更明显：队列里凭空多一行同名文件，状态「无图」，用户会以为工具出了错。

**改法**：`ExpandPaths(paths, suffix, skipDir)` 多一个参数，`WalkDir` 里遇到
`normalizeDir(path) == normalizeDir(skipDir)` 的目录就 `fs.SkipDir`（根目录本身不跳，
否则 `--out-dir` 正好等于源目录时一篇都扫不到）。
`Runner.skipDir()` 只在 `Output == settings.OutputDirectory` 时返回 `OutDir`：
旁挂副本与原地模式的产物本来就散在源目录里，靠后缀过滤就够了。
`normalizeDir` 做 `Abs + Clean + ToLower`——Windows 上用户完全可能把 `--out-dir` 写成 `Out`
而扫描到的是 `out`。

回归测试 `TestExpandSkipsOutputDirInsideScan`：输出目录里的文件被跳过、大小写不同也认得出、
不传 skipDir 时行为不变（3 篇照常扫到）。API 侧同样生效：`POST /api/preview` 传
`settings={output:'directory', outDir:…}` 只回 1 个文件。
## 第 33 轮：`<img srcset>` / `<source srcset>` 里的图，以前一张都不换

**问题**：响应式写法 `<img srcset="img/a.png 1x, img/b.png 2x">` 在 Markdown 里很常见
（Typora、VuePress、Hugo 的图片短代码都会产出），但扫描器只认 `src` 属性，
`srcset` 整条被跳过：界面显示「没有本地图片」，文档原样输出，用户以为跑成功了。

实测（夹具 `%TEMP%\cmp-srcset\doc.md`，5 种写法）：

| 写法 | 改之前 | 改之后 |
| --- | --- | --- |
| `<img src="img/one.png">` | 换 | 换 |
| `<img srcset="img/wide.png 2x, img/narrow.png 1x">` | **不动** | **两张都换**，`2x` / `1x` 原样 |
| `<picture><source srcset="img/wide.png 2x"><img src="img/src.png"></picture>` | 只换 `<img src>` | **两张都换** |
| `<source srcset="img/two.png">` | 不动 | 换 |
| `<img srcset="img/one%2Epng 1x">` | 不动 | 换（百分号编码照常解码） |

预检从「2 处引用 · 2 处待上传」变成「7 处引用 · 7 处待上传」。

**改法**：`parseHTMLImage` 的返回值从「一个 Ref」改成「一组 Ref」，
`<img>` 与 `<source>` 都认；`srcset` 的值按逗号切成一项一项，**只把地址那一段
作为替换区间**，描述符（`1x`、`640w`）和属性的引号逗号全都不动。
`<source src="…">` 是 `<video>`/`<audio>` 的媒体地址，不是图片，**不碰**；
`data:` 开头的 srcset 含逗号，整条跳过（切开会把一个地址切成好几段）。

**顺带的两处解析器提速（负结果：都在噪声内）**：把 `hasPrefixFold` 里
`strings.EqualFold(string(b[:n]), prefix)` 的临时字符串去掉、以及 Markdown/HTML
两个主循环改用 `bytes.IndexByte` 直接跳到下一个 `!` / `<`。
`tools/bench -bench parse` 实测 306 → 304 → 296–304 MB/s，**与改前一致**
（300 篇 / 2.8 MB / 14700→16500 allocs 属测量口径差异），说明瓶颈在系统调用而不是这里。
改动保留了：它让「每个字节都问一次 masked[i]」这种写法不再出现在热路径上。

**回归测试**：`TestScanHTML` 新增 8 个用例（srcset 两项、与 src 并存、无描述符、
带宽度描述符、`<source srcset>`、`<source src>` 不算图、data URI、`<picture>` 里两张）；
`internal/conv` 新增 `TestSrcsetImagesAreAllConverted`（4 处地址全部替换、描述符保留、
输出里不留任何 `img/` 本地路径）。fuzz 60 秒 20,617,368 次执行无失败。
## 第 34 轮：文件名里带 `#` 的图片找不到（顺带纠正上一轮的一个误判）

**先说纠正**：第 32 轮我记了「多级 `..` 解析有问题（`../../` 不行）」，复测后确认**判断错了**。
`posts/post.md` 里的 `../../shared/img/shared.png` 从 `posts/` 出发确实会走到上一级再上一级，
那里没有 `shared` 目录，所以报缺失是对的；`posts/deep/nested/doc.md` 里的 `../../../shared/img/shared.png`
能正常替换。路径解析一直是对的，这条不算 bug，只是我夹具搭错了层级。

**这一轮的真 bug**：磁盘上有 `img/井号#1.png`，文档写 `![井号](img/井号#1.png)` → 报
「找不到文件（本地文件不存在：井号）」。原因是 `imgpath.resolve` 无条件砍掉 `#` 之后的部分
（URL 语义上 `#` 起片段），而 Windows 文件名里 `#` 完全合法，手写路径时谁也不会去写 `%23`。

**改法**：`ResolveAll` 从「两种候选」扩成「四种候选」，让调用方按「文件是否真的存在」挑：

| # | 处理方式 | 命中场景 |
| --- | --- | --- |
| 1 | 解码 + 砍 `?`/`#` | 正常写法（绝大多数） |
| 2 | 不解码 + 砍 `?`/`#` | 文件名真的带 `%20` |
| 3 | 不解码 + 不砍 | 文件名真的带 `#` 或 `?` |
| 4 | 解码 + 不砍 | 文件名带 `#` 且带百分号编码 |

`Resolve`（单值版）保持原语义不变，其他调用点与既有测试不受影响；候选去重时按大小写不敏感比较。

**实测**（夹具 `%TEMP%\cmp-hash`，磁盘上 `img/井号#1.png`）：

| 写法 | 改之前 | 改之后 |
| --- | --- | --- |
| `![井号](img/井号#1.png)` | 找不到文件（`井号`） | **替换成功** |
| `![百分号](img/%E4%BA%95%E5%8F%B7%231.png)` | 替换成功 | 替换成功（两种写法都认） |

**回归测试**：`TestResolveAllKeepsLiteralFallback` 加两组（裸 `#` 的两个候选、带 query 的两个候选）；
`internal/conv` 加 `TestHashInFileNameResolves`（上传 1 张、0 失败、输出里不留本地路径、无提示）。

**性能**：`ResolveAll` 每个引用多做最多 3 次纯字符串解析（没有系统调用），
`tools/bench -bench parse` 与 e2e 都在噪声内；真正的 `os.Stat` 仍被 `fileStamp` 缓存
按小写绝对路径去重，候选变多不会让 stat 次数跟着变多（第一次命中就停）。
## 第 35 轮：解析器 300 → 425 MB/s（`bytes.IndexByte` 跳转 + 不让切片逃逸）

第 33 轮我在 perf-log 里写「两处提速都在噪声内」，**那句话是错的** —— 当时我用的是
「改完之后单次跑几次」，而不是「同一台机器上前后两个二进制交替跑」。改成 A/B 之后
（`git worktree add` 取出改前的提交，分别编译 `bench-before.exe` / `bench-after.exe`，
9 轮交替、取中位），差距非常稳定。

**测量方法**（可复现）：

```powershell
git worktree add $env:TEMP\cmp-wt-before 8f49b4a
# 分别 go build -o bench-before.exe / bench-after.exe ./tools/bench
# 交替跑，参数固定
bench-before.exe -bench parse -files 300 -refs 30 -pool 60 -kb 8 -prose 8 -repeat 21 -quiet
bench-after.exe  -bench parse -files 300 -refs 30 -pool 60 -kb 8 -prose 8 -repeat 21 -quiet
```

**结果（7 轮交替，中位）**：

| 版本 | 吞吐 | allocs/op |
| --- | --- | --- |
| 改前（8f49b4a） | **300 MB/s** | 14700 |
| 改后 | **425 MB/s** | 14700 |

单轮数字：before 308/306/310/282/300/290/299；after 430/432/421/429/425/409/425 ——
没有重叠，不是噪声。

**三处改动**：

1. Markdown 主循环：`for i := 0; i+1 < len(src); i++ { if masked[i] || src[i] != '!' … }`
   → `bytes.IndexByte(src[i:], '!')` 直接跳到下一个 `!`。2.8 MB 的文档里 `!` 大概每
   200 字节才出现一次，逐字节判断等于白跑 200 次。
2. HTML 主循环：同样改成 `bytes.IndexByte(src[i:], '<')`。
3. `parseHTMLImage` 不再自己 `var refs []Ref` 再返回（那会让切片逃逸到堆上，每个
   `<img>` 多一次分配 —— 我第一版就是这个错，allocs 从 14700 涨到 16500），改成把
   结果 `append` 进调用方的 `d.Refs` 并返回它，`srcsetRefs` 同理改成 `appendSrcsetRefs`。

**为什么之前没发现**：第 13 轮我给 `protectedMask` 里的 `<pre>` 扫描做过同样的
`IndexByte` 改造（当时 247 → 299 MB/s），但**主循环这两处一直是逐字节的**，
而它们的迭代次数是全文长度级别的。这次是先把「改前/改后」两个二进制放在一起交替跑，
才看清 300 和 425 的差距。

**功能回归**：`go test ./...` 10 个包全绿；fuzz 45 秒 15,397,894 次执行无失败；
`-bench both -verify` 300/300 全绿、残留本地引用 0、远程/代码块/缺失各 300/300 保留；
e2e 最好 197 ms（中位 204 ms）、峰值堆 18.3 MB —— 解析变快没有让端到端变慢
（端到端本来就卡在建文件上，第 2 轮已经测过）。
## 第 36 轮：解析器 425 → 1290 MB/s（把 `protectedMask` 的逐字节循环全换成跳转，缓冲区进池子）

第 35 轮之后再看 profile，`protectedMask` 一个人占了 43% 的解析时间。它里面有五个
「逐字节走完全文」的循环，而这几个循环要找的字符（换行、`<`、`` ` ``）在正文里
都很稀疏 —— 每篇文档都在为它们白跑几十万次判断。

**A/B（`git worktree add` 取 HEAD=82be45a 编 `bench-before.exe`，5 轮交替）**：

| 版本 | 单轮吞吐（MB/s） | 中位 |
| --- | --- | --- |
| 改前（82be45a） | 417 / 406 / 436 / 406 / 394 | **406** |
| 改后 | 1292 / 1262 / 1293 / 1271 / 1319 | **1292** |

相对最早的基线（第 0 轮 297 MB/s）是 **4.3 倍**；alloc/op 14700 → 13503，
bytes/op 6.3 MB → 2.0 MB（每篇文档少分配 4.3 MB）。

**五处改动，每处都是「别再逐字节问」**：

1. 围栏代码块的行扫描：`for lineEnd < n && src[lineEnd] != '\n'` → `bytes.IndexByte`。
   这个循环**每篇文档都要走一遍全文**，是最大的一处。
2. 找闭合围栏时同样用 `IndexByte` 找行尾。
3. HTML 注释：原来从每个字节开始找 `<!--`，改成先 `bytes.Index(src[i:], []byte("<!"))`
   跳过去 —— 没有注释的文档现在是一次 memchr 扫完，而不是 n 次比较。
4. `<pre>` / `<code>`：先 `bytes.Contains(src, []byte("<"))` 粗筛，没有 `<` 直接跳过
   整段（以前是两轮全文扫描）。
5. 行内代码：`for i := 0; i < n; i++ { if mask.has(i) || src[i] != '`' }` →
   `bytes.IndexByte(src[i:], '`')`。这一处单独把 819 → 1178 MB/s。
6. `indexFold`（找闭合标签）：先跳到首字母（大小写折叠后）再逐字节比较，而不是
   每个位置都试一次 `hasPrefixFold`。

**另外两处分配优化（不是循环，是 GC）**：

- `protectedMask` 的 `make([]bool, len(src))` 每篇文档一次，2.8 MB 文档就是 2.8 MB 垃圾。
  改成 `sync.Pool` 复用（上限 4 MB，超过就不进池子，免得一篇超大文档把内存钉住）。
  profile 里 `runtime.lock2`/`unlock2` 合计曾占两成，主要就是这份分配带来的。
- `indexLines` 的 `[]int` 同样进池子（上限 65536 行）。alloc/op 14700 → 13503 就是这两处。

**试过但回退的**：把掩码从 `[]bool` 换成 `uint64` 位图（省 8 倍内存）。实测**慢 9%**
（641 vs 702 MB/s）——掩码是随机访问的，字节表一次 load 就够，位图每次都要移位掩码。
写在代码注释里，免得以后有人再试一遍。

**功能回归**：`go test ./...` 10 个包全绿；`-race` 不可用（本机 cgo 关着），改用两条
专门盯缓冲区复用的用例：`TestScanRepeatedlyIsStable`（同一篇文档跑 500 遍，引用必须
逐字段一致）与 `TestScanConcurrentReusesBuffers`（32 个协程 × 200 轮并发扫描）。
**这两条用例确实守得住**：把池子里的「清空」那一步删掉，第一条立刻 FAIL
（`第一遍就有 1 个引用，想要 2 个`）。

**端到端**：`-bench both -verify` 300/300 全绿、残留本地引用 0；e2e 最好 196 ms
（中位 202 ms）、峰值堆 18.7 MB（改前 21.8 MB）、totalAlloc 34.6 MB（改前 42.4 MB）。
单篇 5 MB 文档（`%TEMP%\cmp-huge\huge.md`，1250 处引用）跑 CLI：**55 ms → 42 ms**。

## 第 37 轮：拿真实文档复核「解析器快了 4 倍」（不是合成夹具的幻觉）

合成夹具（300 篇里塞 30 处引用、纯色 PNG）是我们自己造的，形状可能对解析器过于友好。
这一轮给 `tools/bench` 加了 `-corpus <目录>`：不造夹具、不写文件，直接把目录里现有的
`.md` 读进来量纯解析。语料取自本机 `D:\Projects` 下 381 篇真实 Markdown（3.83 MB，
含 README、设计文档、日志；1500 篇上限里剩下的不足 200 字节的被过滤掉）。

| 指标 | 改前（`a8a849e^` 的解析器） | 改后 | 变化 |
| --- | --- | --- | --- |
| 吞吐 | 408 MB/s | **1382 MB/s** | **3.4×** |
| `ns/op`（一遍 381 篇） | 9.37 ms | **2.77 ms** | −70% |
| `allocs/op` | 3247 | **2059** | −37% |
| `bytes/op` | 5.59 MB | **133 KB** | **−97.6%** |

`bytes/op` 掉这么多是因为掩码与行首表进了 `sync.Pool`（之前每遍都要按文档长度新分配），
以及切片不再逃逸。合成夹具上同一组改动是 406 → 1292 MB/s，真实语料上比例还略高一点，
说明这些跳转不是靠我们的夹具形状吃饭的。

**端到端与正确性**（1000 篇夹具，进程内假图床，`-fresh -reusefixture -verify`）：
`wall 229 ms`（中位 232 ms）、4359 篇/s、52312 张/s、峰值堆 23.1 MB；
`[verify] 输出文件=1000 已全部替换=1000/1000 残留本地引用=0 远程保留=1000/1000
代码块保留=1000/1000 缺失保留=1000/1000`。

**CLI 真机**（381 篇真实文档 `--dry-run`）：36 ms（空目录 22 ms、`--version` 22 ms）——
扫描 3.8 MB 的增量只有十几毫秒，CLI 现在的成本主要是进程启动。

**新工具** `-corpus` 的用法：`bench.exe -bench parse -corpus <目录> -repeat 30 -quiet`。
注意它只量解析，不做上传/回写，所以不会改动语料目录里的任何文件。

## 第 38 轮：路径解析不再给每处引用算 4 遍（分配 −30%）

第 37 轮的 `-memprofile` 暴露出一个和第 36 轮改解析器无关的热点：**`imgpath` 每处引用都在
做多余的工作**。5000 篇 / 6 万处引用的 e2e 里，`net/url.parse` 占 13%，`filepath.Join`（经
`strings.Builder.WriteString`）占 15%，两者都来自 `ResolveAll` 与 `resolve`：

1. `ResolveAll` 一次算出四种候选（解码+砍后缀、逐字、逐字不砍、解码不砍），再用
   `fileExists` 逐个试。**绝大多数引用第一种就命中**，另外三种纯属白算。
2. `resolve` 对每个候选都无条件 `url.Parse(s)`，只为判断它是不是 `file://`。
3. `Classify` 每个引用都 `strings.ToLower(s)` 一次，7 个前缀判断全部走分配。

改法（`internal/imgpath`）：

- 新增 `ResolveExisting(docPath, target, exists func(string) bool)`：先用主候选问一次
  `exists`，命中就返回；只有不存在时才去算那三种退化写法。runner 的引用解析换成它。

## 第 39 轮：预览响应按需 gzip（5000 篇 11.6 MB → 366 KB）

界面上「把一批文档加进队列」会先请求一次 `/api/preview`，响应里带着每个文件、每张图的
预览明细。1000 篇时是 4.1 MB，5000 篇时是 **11.6 MB** 的 JSON——服务端编得出来（0.17 s），
但浏览器要把这 11.6 MB 下载下来再 `JSON.parse` 一遍，纯属浪费：这些字段高度重复，
压缩比能到 30 倍以上。

改法（`internal/server/server.go`）：新增 `writeJSONFor(w, r, code, v)`，客户端在
`Accept-Encoding` 里接受 gzip 时就边编码边压，同时回 `Vary: Accept-Encoding`；
`/api/preview` 与 `/api/run/current`（刷新接管时那份快照可能同样大）改用它。
`acceptsGzip` 认 `gzip;q=0` 这种「明确不要」，curl 之类不发的客户端拿到的仍是明文。
SSE（`/api/events`）不走这个函数，事件流依然是**不压缩、逐批 flush**。

| 场景 | 明文 | gzip | 压缩比 |
| --- | --- | --- | --- |
| 5000 篇预览（60000 张图） | 11.64 MB | **366 KB** | **31.8×** |
| 10000 条路径预览（含上次产物） | 20.65 MB | 992 KB | 20.8× |
| 1000 篇预览 | 4.13 MB | — | — |

**界面上量到的**（打包版 exe，5000 篇夹具）：把 5000 条路径贴进队列到页脚就绪 **83 ms**；
那次 `/api/preview` 走 366 KB（浏览器解出 11.64 MB）、请求耗时 186 ms，其中 `JSON.parse` 21 ms；
DOM 里仍然只有 11 行（虚拟化），页脚「5000 个文件 · 60000 张图」与命令行一致。

服务端在回环上多花的时间可以忽略（同一请求 0.347 s → 0.354 s，压缩本身约 7 ms）；
真正省下的是浏览器要收、要解、要读进内存的那 11 MB。

**测试** `TestPreviewIsGzippedWhenClientAccepts`：不带 `Accept-Encoding` 必须是明文且
`Vary` 声明依赖；带 `gzip` 必须回 `Content-Encoding: gzip` 且解开后内容不变；
带 `gzip;q=0` 必须不压缩。
## 第 40 轮：松散解析从平方变线性（单行病态文档 377 → 67 ms）

**怎么发现的**：写完引用式图片和 srcset 支持之后，想看看「一整行、没有任何换行」的
文档会不会把扫描器拖慢。夹具是 `%TEMP%\cmp-longline`：一行里连续 N 处「路径带空格」
的松散写法 `![图](imgs/a b1.png)![图](imgs/a b2.png)…`，250/500/1000/2000/4000 处
（6/11/22/46/93 KB）。改之前每篇跑 `--dry-run` 是 **34 / 35 / 55 / 129 / 363 ms**，
减掉约 30 ms 的启动开销后是 4 / 5 / 25 / 99 / 333 ms —— 引用数翻倍耗时为 5× / 4× /
3.4×，明显超线性。

**根因**：`internal/mdscan/scan.go` 的 `looseDestEnd` 以前一路扫到**本行最后一个顶层
`)`**（贪心），每处引用都要扫到行尾 → 一行 N 处就是 O(n²)。顺带还有个正确性问题：
`![a](x.png) 和 ![b](b.png)` 写在一行时，贪心会把 a 的地址算成
`x.png) 和 ![b](b.png`，b 反而漏掉。

**改法**：改成扫到**第一个处于顶层的 `)`** 就收尾；紧跟 `)` 的是引号时不收尾
（那是标题里的括号，`![图](my pic.png "说明(1)")`）；再加 `maxLooseDest = 4096`
兜底，病态输入的开销有上界。`looseTitleStart` 的标题识别逻辑不变。

**数字（`git worktree add` 取 82be45a 编改前二进制，同一批夹具各 3 次取中位）**

| 单行引用数 | 改前 | 改后 | 倍数 |
| --- | --- | --- | --- |
| 1000 | 58 ms | 35 ms | 1.7× |
| 2000 | 126 ms | 44 ms | 2.9× |
| 4000 | 377 ms | 67 ms | 5.6× |

引用越多差距越大，正是 O(n²) → O(n) 的形状。Go 测试里压到 20000 处引用：
一行 489 KB 的一行，`ScanLang` **3.3 ms**（改前要八秒多）。

**正确性复核**：另造 `%TEMP%\cmp-longline2`（100 张真实图片、文件名带空格和括号，
一行里 4000 处引用循环引用它们）→ dry-run 54 ms；真跑 95 ms、**替换 4000 处、残留
本地引用 0**、输出 156 KB。

**回归测试**：`TestLooseRefsShareOneLine`（一行三处，前两处松散、第三处尖括号，
每处只认自己那对括号）、`TestLooseRefsOnAHugeLineAreLinear`（20000 处引用、断言
数量与 3 秒上限，退化回平方会直接失败）。

## 第 42 轮：远程图片检测 + 本地化（补的是功能缺口）

### 为什么做

用户提了两个方向：①「文章图床地址检测（是否有效）」②「文章图片图床本地化（反过来）」。
原来的程序只会一个方向：本地图 → 图床。文章里已经挂出去的图（换过图床、图床跑路、
从别人那儿抄来的文章）一律原样留着，链接死了也没人知道。

### 三种模式

`Settings.Remote` 三档，互斥：

| 模式 | 做什么 | 改文档 | 上传本地图 |
| --- | --- | --- | --- |
| `ignore`（默认） | 远程图原样留着，行为和以前完全一致 | 否 | 是 |
| `check` | 逐个探测远程地址，报告哪些打不开 | 否 | **否** |
| `download` | 下载回文档旁边的子目录，链接改成相对路径 | 是 | **否** |

`check` / `download` 都不上传本地图片 —— 用户要的是「反过来」，这两个模式里本地图保持原样
（明细标「本地保留」）。也正因为不上传，这两个模式**不需要 PicGo 开着**：命令行不再先 Ping，
界面上那盏灯显示中性的「本次不需要 PicGo」（`/api/health` 新增 `picgo.needed`）。

### 实现

新包 `internal/remoteimg`（14 条测试）：

- `Probe`：先 HEAD（省流量）；HEAD 成功但类型不是图片、或状态可疑时再 GET 前 512 字节做内容嗅探
  —— 否则用 `application/octet-stream` 发图的图床会被整片误判成坏的。404/410 不再重试，
  连不上也不重试（GET 也是同样结局）。
- `DownloadTo`：**边读边嗅探**，开头不是图片直接 `ErrNotImage`（绝不把 HTML 错误页存成 `.jpg`），
  超过 64 MB 报 `ErrTooLarge`，非 2xx 带状态码返回。
- `Ext`：优先按真实内容给后缀（`image/png` → `.png`），退化到地址后缀，再退 `.png`。

`internal/conv/remote.go`：本地上传和远程检测/下载**共用一个工作池与一个进度条**（`runUnits`
取代了原来的 `uploadGroups`）；同一个地址一轮只问一次（`remoteFiles` 表 + `done` 通道），
跨文档复用时同目录直接复用、不同目录复制一份；下载走临时文件 `.cmp-remote-*.tmp` 再改名，
已存在且大小一致就跳过重写。

### 实测

夹具 `%TEMP%\cmp-remote-e2e\doc.md`：1 张本地图 + 2 个有效远程地址（同一张图，其中一处带标题）
+ 1 个 404 + 1 个不存在的域名 + 1 个返回 HTML 的地址。

- `--remote check`：`远程图 5 张，失效 3 张`，逐行说明「HTTP 500」/「连不上这个地址：… EOF」，
  文档一个字节没改，`images/` 目录没建。退出码 0（只检测，不算失败）。
- `--remote download`：`下载 2 张远程图，3 张失败`，`images/` 里落了一张 197,493 字节的 PNG，
  输出文档里两处链接变成 `images/20261109092351916.png`（标题 `"这是标题"` 原样保留），
  三处失败的**保持原远程地址**，源文档未改。退出码 1（有失败）。
- GUI（打包版 exe，Playwright）：设置弹窗里出现「文章里的远程图」三选，切到「下载回本地」后
  出现子目录输入框；跑完页脚「2 个文件 · 4 张图 · 失败 1 · 下载 2」，逐图明细
  「本地保留 / 已下载 → assets/…png / 下载失败 HTTP 500」；`check` 模式页脚
  「检测 3 个远程地址 · 其中失效 1」，行状态「已检测」，没有「输出」行（确实没写文件）。

### 顺带修掉的说法问题

- 命令行在下载模式下把失败说成「上传失败」→ 改成「失败」（错误文案自己已经以「下载失败：」开头，
  再叠一层就成了「下载失败  上传失败  下载失败：HTTP 500」）。
- 界面逐图状态同理：远程地址的失败显示「下载失败」，本地图片的失败仍是「上传失败」。
- 明细聚合行在只碰远程图的模式里不再显示「0 替换」（那是句废话），换成「N 下载 / N 本地保留」。
### 第 42 轮的补丁：协议相对地址 + 检测重试

`//cdn.example.com/x.png` 这种写法（网页里靠页面协议补全，Markdown 里没有页面协议可言）
原来被判成「不是 http/https」直接跳过。现在 `remoteimg.Normalize` 统一补 `https:`，
猜错了（老图床只开 http）再退回 `http:` 试一次；下载路径同样处理。

检测模式还加了**一次重试**（400 ms）：CDN 偶发 502 / 连接被重置都会让一个好好的地址
被打上「失效」，这是检查器最招人恨的误报。404/410 这种确定的结论不重试。
代价是 check 模式在真出错时慢 400 ms —— 夹具里 4 个地址 1.6 s（原本 1.1 s，多的就是重试等待）。

测试：`TestNormalizeAddsSchemeToProtocolRelative`、`TestRemoteDownloadHandlesProtocolRelativeURL`、
`TestProbeRetriesTransientFailures`（第一次 502、第二次成功，断言正好请求 2 次）、
`TestProbeDoesNotRetryDefiniteMisses`（404 只请求 1 次）。
### 第 42 轮的补丁 2：下载的图要跟着输出文档走

`-o directory --out-dir out` 配 `--remote download` 时，图片被下到了**源目录**旁边的
`images/`，而文档写到了 `out/` —— 输出文档里的 `images/x.png` 直接是断链，源目录还多出
一个没人用的 `images/`（实测：`\docs\images\…png` + `\out\a.md`，`a.md` 里写着 `images/…png`）。

改法：新增 `Runner.remoteBaseDir(src)` —— 目录模式下返回 `OutDir` 的绝对路径，其余模式
（旁挂副本、原地替换）仍返回源文件所在目录。`runUnits` 的基准目录由 `filepath.Dir(path)`
换成它。

回归：`TestRemoteDownloadFollowsOutputDirectory`（断言图落在 `out/images/`、源目录旁
没有 `images/`、输出文档里的链接是 `images/ok.png`）；另手动复核 sidecar 模式仍然把图放在
源文件旁边（`\images\…png` 与 `\a.converted.md` 同级）。
### 第 42 轮的补丁 3：并发、父级目录、规模

- **下载并发跟随 `-c`**：200 张不同地址、每张 200 ms 的假图床，`-c 1 → 41515 ms`、`4 → 10456`、
  `8 → 5395`、`16 → 2885`、`32 → 1594`，与 `200×200ms÷c` 的理论下限（40000/10000/5000/2500/1250）
  逐条吻合 —— 远程下载与上传共用同一个信号量，调大并发直接见效。
- **`--remote-dir ../assets` 可用**：写到文档的上一级，写回文档的链接是 `../assets/…png`；

- **规模**：20 篇 × 30 处远程引用（只有 3 个不同地址）→ check **3.1 s**（600 处引用只发 3 次请求，

### 第 42 轮的补丁 5：远程图也做跨运行缓存

上传侧第 4 轮就有缓存了，下载侧一直漏着：第二次跑同一批文档，每张图都要完整 GET 一遍，
再拿本地文件比大小。200 张图（每张 200 ms 的假图床、`-c 16`）冷跑 2938 ms，热跑还是 2 秒多。

新增 `internal/remotecache`（与 `uploadcache` 同构）：键是「地址 + 目标目录」
（同一个地址在不同目录下是不同的本地文件，不能混用），值是上次的文件名与字节数。
命中条件是**本地文件真的还在、大小也对得上** —— 缓存文件本身不参与判断，
所以图床上的图被换掉也不影响：我们复用的是自己下过的那份。

- `Lookup` 在 `downloadRemote` 最前面：命中就直接返回，连网络都不碰。
- `Store` 在落盘成功（或「已有同样大小的一份」）之后记一笔。
- `Save` 会先把磁盘上已有的条目读回来合并（界面和命令行可能同时在跑）。
- 失败的结果**不记**：图床恢复了下次还要再试。

实测（200 张、每张 200 ms、`-c 16`）：冷 **2938 ms → 热 23 ms**（`省下 200 张下载`）；
20 篇 × 30 处引用（1 张有效图）：2497 ms → **1077 ms**（剩下的时间是那 200 个必然失败的
HTTP 500 在重试）。缓存命中时输出文档照常改写（链接仍然指向本地文件），落盘图片数不变。

测试 7 条：同目录命中、换目录不命中、地址/路径大小写不敏感、保存后重开还记得、
保存时合并磁盘上的旧条目、空名字/零大小不记、关掉与 nil 缓存都安全、
陈旧条目按 TTL 清理、超过上限按最后使用时间淘汰。
界面上也核了一遍（打包版 exe 端口 17997，`remote=download`）：第一次跑页脚「1 个文件 · 1 张图 ·
下载 1」，同一个文件再跑一次变成「1 个文件 · 1 张图 · **省下 1 张下载** · 下载 1」——
缓存命中在界面上是看得见的，用户不会以为「怎么这么快，是不是没跑」。
### 第 42 轮的补丁 6：一个开关管两件事

下载缓存跟上传缓存共用 `ReuseUploads`（`--no-reuse` 一起关掉）：对用户来说这是同一件事
——「上次做过的别再重复做」，拆成两个开关只会让人猜「我到底关对了没有」。
实测：默认第二次跑报「省下 1 张下载」、0.0 s；加 `--no-reuse` 之后重新下载，2.0 s、不再报省下。
`-o in-place` 配 `--remote download` 也复核过：文档被原地改写、`a.md.bak` 里有原件、
图片落在同级的 `images/`。
### 第 42 轮的补丁 7：几处边角的说法与实测

- **check 模式的并发扩展**（200 个不同地址、每张 200 ms 的假图床）：`-c 1 → 40666 ms`、
  `4 → 10062`、`8 → 5048`、`16 → 2636`、`32 → 1434`，与 `200×200ms÷c` 吻合 —— 检测和下载、
  上传共用同一个信号量。
- **带查询串的地址**（`?x-oss-process=…`、`?v=2`、`#frag`，阿里云 OSS / 七牛很常见）：
  三处都下载成功，落盘成 `…png`、`…-2.png`、`…-3.png`（同地址不同查询串算不同的图，
  不能共用文件名），链接全部改成本地相对路径。
- **预检不打网络**：50 张远程图、check 模式，`/api/preview` **4 ms** 返回（50 条 item 状态都是
  `remote`）—— 用户一边打字一边预览，不能每敲一下就去问图床。
- **下载目录的位置被同名文件占了**：原来报的是系统原话「mkdir …: The system cannot find the
  path specified.」（谁也看不懂），现在说「本地目录 … 已经被一个同名文件占了，放不进图片
  （换个目录名，或先挪走那个文件）」，英文同构；`TestRemoteDirCollidesWithFile` 守着这条。
### 两个不同地址、同一个文件名：第二张会把第一张悄悄覆盖

复现（真机，图床可用）：

1. `a.md` 引用 `https://webp.mus.pp.ua/test_storage/20261109092351916.png`（197,493 B，
   SHA-256 `2AB43E05…`），落地 `images/20261109092351916.png`；
2. `b.md` 引用 `http://127.0.0.1:36691/pic/20261109092351916.png`（70 B，**同名不同内容**）。

第二遍跑完，`images/20261109092351916.png` 变成了那张 70 B 的图，而 `a.converted.md` 里写的
还是 `images/20261109092351916.png` —— 文档没报错、没提示，只是图片悄悄换成了另一张。
这类问题最难发现：**没有任何一处失败，产物看起来完全正常。**

根因在 `remoteFileName`：它只在 `r.remoteNames`（**本轮运行的内存表**）里查重名，
跨运行留在磁盘上的同名文件它一无所知；而 `downloadRemote` 里那句「大小一致就跳过重写」
只对**同一个地址**成立，不同地址大小不同就直接 `os.Rename` 覆盖。

改法两条，缺一不可：

- 缓存开着时按**归属**判断：`remotecache` 新增 `Owner(dir, name) (rawURL, size, ok)`，
  用 `lower(url) + "\x00" + lower(clean(dir))` 这个 key 结构反查「这个目录里这个名字
  上次是哪个地址下的」，归属不同就换下一个候选名；
- 缓存关掉时（`--no-reuse`）退一步看磁盘：同名文件存在、大小和这次下下来的不一样，
  那它肯定是另一张图。

回归测试 `TestRemoteDownloadDoesNotOverwriteDifferentImage` 与
`TestOwnerFindsTheUrlBehindAName` 都是**先写、先看到 FAIL**（`先下载的那张图被后来的同名图覆盖了`）
才改的代码。真机复验：`b.converted.md` 变成 `![二](images/20261109092351916-2.png)`，
`images/` 里 `20261109092351916.png 197493` + `20261109092351916-2.png 70`，
第一张的 SHA-256 仍是 `2AB43E05…`；`--no-reuse` 走磁盘那条路也得到同样的 `-2` 后缀。
### 死链检测：域名解析不出来不该重试

`worthRetrying` 原来把「所有传输层错误」都当成瞬时抖动，于是一条根本不存在的域名
也要白等 400ms 再试一遍。一篇文章里有几十条死链时，检查器会慢到没人愿意用：
200 条 `no-such-host-N.example` 实测 **15.2 秒**。

改法分两层，因为不同网络对「域名不存在」的回报不一样：

- 拿到 `*net.DNSError` 且不是超时/临时错误 → 确定结论，不重试；
- 本机（以及公司代理、运营商 DNS 拦截）会把「域名不存在」回成 `EOF`，拿不到 DNSError。
  这类错误的共同点是**发生在还没开始说话之前**，用 `res.Status == 0` 加上
  「EOF / ECONNREFUSED / ECONNRESET / `net.OpError.Op == "dial"`」来认，
  同样算结论已定。

真正的瞬时抖动（对方 502、读到一半断开）会有状态码或发生在读取阶段，仍照旧重试一次。

复测：同样 200 条死链 **15.2 秒 → 8.3 秒**。剩下的时间是 DNS 解析本身的延迟
（200 个不同域名，16 路并发分担），没法再压。
### 三个「看起来正常、其实是坏的」远程图分支

拿一台本地静态服务器造了三种坏响应，逐个看工具怎么说：

| 服务器回什么 | 改之前 | 改之后 |
| --- | --- | --- |
| 200 + `text/html` 的页面 | 下载模式：`这个地址返回的不是图片（%s）` —— **`%s` 没被替换** | `这个地址返回的不是图片（text/html; charset=utf-8）` |
| 200 + `Content-Type: image/png` + **0 字节** | 下载模式：**算成功**，磁盘上留下一个 0 字节的 `empty.png` | `这个地址能打开，但内容是空的（0 字节），不是一张能用的图片` |
| 200 + 70 MB 的 `big.png` | 正确报「太大了（超过 64 MB）」 | 同左 |

两个真 bug 的来历：

- **`%s` 没被替换**：`remoteOutcomeDownload` 里 `i18n.T(lang, i18n.KeyConvRemoteNotImage)` 忘了传参，
  而 `T` 只在 `len(args) == 0` 时原样返回文案，于是格式动词就留在屏幕上。
  顺手把「实际拿到的是什么类型」这件事做成 `remoteimg.NotImageError{Kind}`（带 `Is` 方法，
  `errors.Is(err, ErrNotImage)` 照样成立），下载与检测两条路径都能说出具体类型。
- **0 字节算成功**：`DownloadTo` 原来只在 `n > 0` 时嗅探类型，`n == 0` 时 `res.OK()` 靠
  `Content-Type: image/png` 就判成功。现在 `DownloadTo` 先判空正文（`ErrEmpty`），
  `Result.OK()` 也把 `Size == 0` 算成不可用 —— 否则**检测模式会说「全部有效」，
  用户下载完才发现图是空的**，这比直接报错糟糕得多。

新增测试：`TestDownloadRejectsEmptyBody`、`TestNotImageCarriesTheActualType`。
### 「同名 + 同大小」才是最难发现的那种撞车

上一轮修掉了「两个地址都叫 `pic.png`、大小不同」的覆盖。可**两张不同的图完全可能一样大**（同尺寸、同压缩率），
而当时判断「磁盘上这个同名文件是不是同一张图」用的是大小。于是：

- `--no-reuse`（缓存关掉、反查不到归属）时，第二篇文档会把第一篇的图**覆盖**掉，第一篇的链接悄悄指向另一张图；
- 跨目录复用那条路（`placeRemoteFile`）也一样：目标目录里躺着一张同名同大小的旧图，就被当成「已经搬过了」，
  新文档指向的是别人那张图。

改法：两处都改成**逐字节比对**（新增 `sameFile(a, b)`，先比大小再读文件，大小不同立刻返回）。
`remoteFileName` 现在需要拿到「刚下到临时文件里的那份内容」才能判断，所以多一个 `fresh` 参数。

两条回归都是先写用例、看到 FAIL 才改代码，改完再把修复临时换回「只比大小」确认用例会红：

- `TestRemoteDownloadDoesNotOverwriteSameSizeImage`（`--no-reuse`，同目录）
- `TestRemoteCopyToOtherDirReplacesWrongSameSizeFile`（跨目录复制那条路）

真机复验：两张 268 字节、SHA-256 分别是 `60503F77…` 与 `D6CAB07E…` 的 PNG，同名 `pic.png`，
第二次运行得到 `pic.png` + `pic-2.png`，`b.converted.md` 指向 `images/pic-2.png`，第一张一个字节没变。
### 远程下载原来没走全局并发闸门

上传一直抢 `r.sem`（`internal/conv/runner.go:841-848`），远程下载却是直接发请求：
`handleRemote` 的领头者分支根本没有 `select { case r.sem <- struct{}{} }`。
于是并发只受「每篇文档几个 worker」限制 —— 50 篇 × 16 就是 800 个请求同时在飞，
图床只会回 429 或者干脆封 IP。

测量（`imgsrv -delay 100ms`，40 篇 × 25 张不同地址 = 1000 次下载）：

| | `-c 16` 墙钟 | 反推并发 | 理论下限 |
| --- | --- | --- | --- |
| 改之前 | 1417 ms | **≈71** | 6250 ms |
| 改之后 | 7431 ms | ≈13 | 6250 ms |

（改之前那次用的服务器没有延迟，所以按 100ms 反推才显得夸张；改之后换成真带 100ms 延迟的
实例复测，`-c 16` 7431 ms、`-c 4` 27411 ms，与 `1000×100ms÷c` 对得上。）

改法只有五行：领头者分支在 `switch r.remoteMode()` 之前抢 `r.sem`，`defer` 里还回去。
等结果的那些协程（`rf.done` 分支）不占额度，所以不会自锁 —— 这一点和上传那边是同一个道理。
### 下载回来的链接带空格时，我们自己写出去的 Markdown 是坏的

远程地址里常有 `%20`（`/img/4 x.png` 就是这么来的）。下载后文件名沿用地址最后一段，
于是本地路径里就有了空格；写回文档时却只把地址原样塞进 `![alt](…)`。

CommonMark 里 `![a](images/4 x.png)` 的地址在第一个空格处就结束了，后面那截既不是合法标题，
于是**整张图不显示**。也就是说：我们把图好好下载下来了，却写了一条渲染器认不出的链接。

改法：Markdown 行内写法的地址里若含空格或括号，就用尖括号包起来
（`![a](<images/4 x.png>)`）—— 这本来就是 CommonMark 给这种路径准备的正规写法。
引用式（`![alt][label]`）原本就走 `wrapURL`，HTML 的 `src="…"` 不需要处理。

回归 `TestRemoteDownloadWrapsSpacedLinkInAngleBrackets`：改前输出 `![空格](images/4 x.png)`，
改后 `![空格](<images/4 x.png>)`；把 `wrapURL` 那一支临时去掉，用例立刻红。
## 被强杀之后留下的临时文件

写盘和下载都是「写临时文件 → 改名」这个套路：写一半崩了不会留下半个文档，
代价是进程被强行打断时临时文件会留在原地。优雅取消没问题（defer 会删），
但任务管理器结束进程、关窗口时系统直接杀、断电，defer 就不存在了。

实测：--remote download 跑 900 ms 后 `Stop-Process -Force`，images/ 里留下
两个 **0 字节**的 `.cmp-remote-*.tmp`，而且永远留着 —— 用户看到的是
「我的图片目录里多了几个看不懂的怪文件」，还不知道能不能删。

改法（`internal/conv/temp.go`）：往某个目录写东西之前，顺手把这个目录里
**超过一小时**的 `.cmp-*.tmp` / `.cmp-remote-*.tmp` 删掉。

- 只删超过一小时的：正在写的临时文件刚建出来，年龄是秒级，绝不会被误伤。
- 每个目录一小时最多扫一次（`sweptDirs` 用 `sync.Map` 记时间戳）：
  一次运行会往同一个目录写几千个文件，每个都 `ReadDir` 一遍就是 O(n²)，
  而这里要治的只是一天里可能留下的几个垃圾文件。
- 扫不干净也不算错：这是卫生，不是正确性的一部分，所有错误都忽略。

实测：目录里造两个两小时前的临时文件 → 跑一次 download → 只剩 `中文图片.png`。
3000 篇 / 66000 张图 e2e **850 ms（中位 880 ms）**，300 篇那档仍是 190 ms ——
清扫没有进入热路径。
## 缓存上限从 4000 提到 20000

`remotecache` 原本的上限是 4000 条，注释写着「一个博客几千张图足够」。这个判断是错的：
上限按「条数」砍，砍法是按最后使用时间留最近的 —— 一篇 20000 张图的文档跑完，
前 16000 条当场被淘汰。于是第二篇文档、第二次运行，一张都命中不了。

实测（`%TEMP%\cmp-owner-scale3\big.md`，20000 个唯一地址，`imgsrv` 每张 0 延迟，`-c 16`）：

| 上限 | 冷跑 | 热跑 | 热跑省下 |
| --- | --- | --- | --- |
| 4000 | 36.6 s | **23.1 s** | 4000 张 |
| 20000 | 37.5 s | **0.1 s** | 20000 张 |

代价是缓存文件变大、启动时多读一点。实测（临时 `measure_tmp_test.go` 量的，量完删掉）：

| 条数 | 文件 | `Open`（读盘 + 解析 + 建索引） | `Save`（合并 + 淘汰 + 序列化 + 落盘） |
| --- | --- | --- | --- |
| 4000 | 0.8 MB | 11 ms | 8 ms |
| **20000** | **4.0 MB** | **28 ms** | **21 ms** |
| 50000 | 10.0 MB | 56 ms | 49 ms |
| 200000 | 39.9 MB | 231 ms | 222 ms |

一轮只写一次，21 ms 换掉几十秒的重复下载很划算；再往上才开始伤启动时间（`Open` 在
`NewRunner` 路径上，200000 条那档要多等 0.2 秒）。所以定在 20000。

顺带修掉的：`Owner`（「这个文件名被别的地址占了吗」）原本是全表遍历，4000 条时
**39 µs/次**，而每下载一张图都要问一次。加了 `byName` 反查表（`目录+文件名 → cacheKey`）
之后是 **229 ns/op**（`BenchmarkOwner60k`），与 `Lookup`（418 ns）同量级。索引在
`Open`、`Store`、`Save`（合并磁盘条目后）三处重建，三条回归各盯一个：
`TestOwnerSeesEntriesMergedFromDisk`、`TestStoreReleasesTheOldName`、`TestPruneAlsoClearsTheIndex`。

## 远程图下载：那 2 毫秒不是网络，是 fsync

远程下载一开始是「每张图 2.1 ms」，看着像是网络开销，于是先做 CPU profile 看是谁在吃时间。

2000 处远程引用（本地 `httptest` 服务器回 67 字节 PNG，`-c 16`）：**4.29 s**。
`go tool pprof -top` 里 `runtime.cgocall` 占 98.5%，拆开是：

| 调用 | 占比 |
| --- | --- |
| `os.CreateTemp` → `syscall.createFile` | 28.1% |
| `internal/syscall/windows.MoveFileEx`（`os.Rename`） | 27.2% |
| `os.(*File).Sync` | 26.1% |
| `os.Stat` | 8.6% |
| `os.MkdirAll` | 5.9% |
| `remoteimg.(*Client).DownloadTo`（真正的网络） | 4.2% |

网络只占 4%，剩下全在文件系统。四种写盘方式各跑 2000 张（单张 67 字节）：

| 写法 | 总耗时 | 单张 |
| --- | --- | --- |
| 临时文件 + `Sync` + 改名（原来的做法） | 4.75 s | 2.38 ms |
| 临时文件 + 改名（去掉 `Sync`） | **542 ms** | **0.27 ms** |
| 直接 `O_CREATE\|O_EXCL` 写 | 278 ms | 0.14 ms |
| 直接写 + `Sync` | 3.05 s | 1.52 ms |

`Sync` 一项就是 88% 的时间。它买到的是「断电之后这张图不会只剩半截」——
而图片是可再生的缓存，文档本身（`writeAtomic`）反而没有 fsync，却比图片重要得多。
权衡下来去掉它：真断电了最坏是多一张坏图，重跑一次补回来；而每个用户每一次都要付这 2 ms。

「临时文件 + 改名」保留：改名本身是原子的，目标文件不会变成半截。

真机 A/B（2000 处 `http://127.0.0.1:36692/img/<n>`，`--remote download -c 16 --no-reuse`，各两轮）：
**4023 / 3950 ms → 874 / 612 ms**。产物复核：2000 个文件、0 个 0 字节、0 个残留 `.tmp`，
输出文档 2000 行链接逐条对得上。

### 顺带发现的真 bug：残骸不会自愈，还会把好图挤成 `-2`

验证时把 `images/0.png` 截成 0 字节再跑一次，结果输出变成 `![p0](images/0-2.png)`、
目录里 2001 个文件，那个 0 字节的 `0.png` 永久留着。

根因是上一轮为「不覆盖别人的图」加的保护：同名文件内容不同就换下一个候选名。
可**残骸**（0 字节、写了一半、同步盘只同步了一半）和「另一张同名的图」在它眼里没区别，
于是好图被挤成 `pic-2.png`，坏文件永远不会被替换，文档链接每跑一次漂一次
（`pic.png → pic-2.png → pic-3.png`）。

改法分两层：

- **是我们自己的名字就必须沿用**：缓存里记着这个地址就落在这个名字上（`Owner` 反查），
  那哪怕文件已经损坏或截断也要覆盖它 —— 那正是要修的东西。
- **残骸不算被占**：新增 `looksComplete`，读前 12 字节认格式、读最后 32 字节找终止标记
  （PNG `IEND`、JPEG `FF D9`、GIF `3B`、WEBP 按 RIFF 头里的总长度、BMP 按头里的文件大小）。
  认不出格式的一律当「完整」—— 宁可多留一个 `pic-2.png`，也不能覆盖用户的图。

第一版写的是「终止标记正好在最后 12 字节」，直接把
`TestRemoteDownloadDoesNotOverwriteSameSizeImage` 打红了：那个夹具是「正常 PNG + 尾部追加 1 字节」，
而现实中确实有工具在图片后面追加校验值，那种文件照样能显示。所以放宽成「最后 32 字节里能找到」。

回归 `TestRemoteDownloadHealsTruncatedFile` 四个子用例（缓存开着/关着 × 0 字节/半截）：
先正常下一遍，再把 `images/ok.png` 写成空或 `pngBytes[:len/2]`，第二次跑断言链接仍是
`images/ok.png`、文件补回原大小、且**不存在** `ok-2.png`。

### 连接池：默认只有 2 条空闲连接

`remoteimg.New` 原来不设 `Transport`，走 `http.DefaultTransport`，它的
`MaxIdleConnsPerHost` 是 2；而下载并发默认 16 —— 多出来的连接用完即关，
下一张图重新 TCP + TLS 握手。

本地 HTTPS（`httptest.NewTLSServer`，16 路并发 200 次探测）：
`IdlePerHost=2` **33.2 ms / 新建 87 条连接**；`IdlePerHost=32` **14.0 ms / 新建 29 条**。

真实站点上收益不明显（picsum 每张本来要 ~1 s 服务端时间，握手被淹没：旧 11.98/12.83 s，
新 12.73/12.41 s，打平），但代价是零，所以保留：新增 `newTransport(idlePerHost)` 与
`SetConcurrency(n)`（`NewRunner` 里按实际并发设置；必须在发请求前调用，
`Transport` 字段本身不是并发安全的）。

## 逐图明细：两万行明细一次全画出来

队列那一行展开之后，下面会列出这个文件里每一张图的处理结果。这部分一直是
`v-for` 全量渲染 —— 一篇两万张图的文档展开时，浏览器要一次性造出 **23000 个
`.items__row`、184164 个 DOM 节点**，JS 堆从 8 MB 涨到 95 MB，展开本身耗时
**2058 ms**，而这中间用户能看见的只有十几行。

改成窗口化渲染：超过 `VIRTUAL_THRESHOLD = 200` 条时，列表固定 `ITEM_VIEWPORT = 420px`
高、行高 `ITEM_HEIGHT = 30`、上下各留 `ITEM_OVERSCAN = 8` 行余量，只把
`items.slice(start, end)` 渲染出来，用两个撑高的空 `li` 保住滚动条长度。

| | 改之前 | 改之后 |
| --- | --- | --- |
| 展开耗时（20000 条） | 2058 ms | **26 ms** |
| `.items__row` 节点 | 23000 | **30** |
| DOM 节点总数 | 184164 | **387** |
| JS 堆 | 95 MB | **8 MB** |
| 连续滚动最差帧 | — | 10 ms（p95 8 ms） |

阈值取 200 是因为「一眼能扫完」和「要找某一条」的分界线大概在那儿；边界实测
`exact200.md` 仍然全渲染（200 行、无滚动、无占位 `li`），`exact201.md` 立刻进窗口
（30 行、`max-height:420px`、`scrollHeight 6030`）。

## PicGo 那盏灯：不用的东西不该标红

只检测 / 只下载远程图时压根不上传，PicGo 掉线是**正常状态**。原来那盏灯只看
`online`，于是这种模式下它红着——用户会以为出了故障。后端早就有
`picgo.needed`（`settings.Remote` 不是 `check`/`download` 且非试运行时为真），
只是前端没用。现在三种状态分开：`online` 绿、`needed && !online` 红、
`!needed && !online` 灰并写「本次不需要 PicGo」。
## 下载也要重试：一次 503 不该在文档里留个断链

检测模式第 42 轮一开始就有重试（\probeRetry\：5xx / 429 / 连接被重置再试一次，
等 400 ms），下载模式却一直是一次判死。两者的代价差得很远：检测错了只是报告上
多一条红字，点开一看还是好的；下载错了是**文档里留下一个远程地址**——用户得
自己发现、自己重跑。

所以 \emoteimg.DownloadTo\ 现在也重试，但比检测多做两件事：

1. **最多试 3 次**（400 ms、800 ms 退避），不是 2 次。丢的东西不一样。
2. **重试前把写入目标退回开头**。下载是边读边写，第一次可能已经写进去半张图；
   直接重来会把两次的内容拼在一起，得到一个「大小对、打不开」的文件——这比
   下载失败糟得多。\ewind\ 只认「能截断 + 能定位」的目标（\os.CreateTemp\
   出来的文件就是）；退不回去的目标（\ytes.Buffer\ 之类）宁可报错也不拼。

判断「值不值得再试」这件事，检测和下载共用 \worthRetrying\，这次把三个分支
说清楚了：

| 拿到的东西 | 重试 | 为什么 |
| --- | --- | --- |
| \statusError\（对方回了状态码） | 只有 5xx / 429 | 403/404/410 是对方的结论，问三次还是那句话 |
| 状态码 2xx 但读正文时断了 | 是 | 最典型的「再试一次就好」：对方掐连接、代理超时 |
| 连接阶段就 EOF / 拨号失败 | 否 | 拦截型 DNS 与「域名不存在」同义，白等 |
| \ErrNotImage\ / \ErrEmpty\ / \ErrTooLarge\ | 否 | 拿到完整答复之后的结论 |
| 往本地写失败 | 否 | 磁盘满、文件被占用，跟对方没关系 |

真机验证（\%TEMP%\cmp-flaky-srv\ 那个会抖的小服务器，前 2 次回 503）：

- 前 2 次 503、第 3 次正常 → 下载成功，落盘 67 字节，文档写成
  \![抖两下](images/flaky.png)\，总用时 1.2 s（就是那两次退避）。
- 第一次 \Content-Length\ 声明完整却只写 20 字节再断开 → 重试后文件是完整的
  67 字节，不是「20 + 67」拼起来的 87 字节。
- 健康的 50 张图（\-fail 0\）**44 ms**，重试逻辑不在热路径上。

回归测试：\internal/remoteimg/remoteimg_test.go\ 的
\TestDownloadRetriesServerErrors\、\TestDownloadDoesNotRetryDefiniteMisses\、
\TestDownloadRetriesTruncatedBody\、\TestDownloadRefusesToRetryUnrewindableTarget\，
以及 \internal/conv/remote_test.go\ 的
\TestRemoteDownloadSurvivesOneTransientFailure\（走完整 Runner 的那条路，
夹具新增 \/flaky.png\：第一次 503、第二次正常）。把 \downloadAttempts\ 改回 1，
这五条里四条立刻红——包括 Runner 那条报「所有本地图片都处理失败，未生成文件」。

## 复制别人的图，也不能盖掉别人的图

「同一张图只下载一次，其它文档复制过去」这条捷径有个洞：复制时目标文件名是
写死的 `filepath.Base(srcAbs)`，`sameFile` 不一致就直接 `copyFile` 覆盖。
下载那条路早就走撞名规则（`pic.png` → `pic-2.png`），复制这条路绕过了它。

真机复现（\srv/s1/pic.png\ 与 \srv/s2/pic.png\ 同为 68 字节、内容不同，
hash `CAE90068` / `D9E5D4FC`）：

| 轮次 | 输入 | 结果 |
| --- | --- | --- |
| 1 | `dirB/c.md` → `s2/pic.png` | `dirB/images/pic.png` = `D9E5D4FC` ✓ |
| 2 | `dirA/a.md` + `dirB/b.md` → `s1/pic.png`（`-c 1`，a 当领头者，b 走复制） | `dirB/images/pic.png` **被改成 `CAE90068`** ✗ |

第二轮的受害者是 `c.md`：它那一轮早就跑完了，`c.converted.md` 里的
\images/pic.png\ 从此指向另一张图，而**没有任何一处会报错**，也不会有人
回头检查已经跑完的文档。这种「悄悄改坏历史产物」的错误比下载失败严重得多。

改法：把 `remoteFileName` 里那段候选循环抽成 \pickName(dir, rawURL, base, fresh)\
（本轮内存表、缓存归属反查、残骸判定、序号、\remote-<hash>\ 兜底都在里面），
下载和复制两条路都走它。复制前先 \sameFile\，一致就直接返回；不一致才
\pickName\ 要一个没被占的名字。

改完的实测（同一夹具、同一个命令）：\pic.png\ 仍是 `D9E5D4FC`，
\pic-2.png\ 是 `CAE90068`，\c.converted.md\ 与 \b.converted.md\ 各自指对。

顺带修掉一条**断言方向反了**的旧测试：\TestRemoteCopyToOtherDirReplacesWrongSameSizeFile\
原本要求「b 目录的 pic.png 变成新图」——那正是 bug 的行为。改成要求
`pic.png` 保持原样、新图落在 \pic-2.png\。另加
\TestRemoteCopyDoesNotClobberAnotherDocsImage\ 覆盖上面那个真实场景
（跨目录、并发 1、a.md 排前面保证 b 走复制路径）。
