# 性能迭代记录

这份文件记录每一轮性能优化的**测量方法与前后数字**。所有数字都由 `tools/bench`
（造夹具 + 假图床）与真实 PicGo 现测得出，可以重跑复现。

## 怎么复现

```powershell
# 假图床：300 篇文档 × 每篇 30 处本地引用 × 图片池 60 张 × 8 KB 正文（约 2.8 MB）
go run ./tools/bench -bench both -files 300 -refs 30 -pool 60 -kb 8 -prose 8 -repeat 21 -verify

# 换成真实 PicGo（会真的上传，注意图床额度）
go run ./tools/bench -bench e2e -endpoint http://127.0.0.1:36677 -files 3 -refs 5 -pool 4 -kb 1 -verify

# 拆分阶段：只扫描分类（不写盘、不上传）
go run ./tools/bench -bench e2e -dryrun -files 300 -refs 30 -pool 60 -kb 8 -prose 8 -repeat 21
```

`-fresh` 表示每轮开始前删掉上次的输出（量「首次写入」），不加则是覆盖已有输出。
`-cpuprofile` / `-memprofile` 交给 `go tool pprof` 看热点。

## 测量环境

- Windows + Go 1.24，本地 SSD；夹具目录在 `%TEMP%`。
- 机器上有杀毒软件的实时防护，**首次创建文件的耗时会飘**（最好值 50 ms，偶尔冲到 320 ms），
  所以每轮跑 21 次，看最好值与中位数，别只看单次。
- 假图床是进程内的 `httptest` 服务器，网络耗时可以忽略；真实图床的数字另列一节。

## 第 0 轮：基线

夹具：300 篇 / 9600 处引用 / 2.8 MB，并发 4。

| 指标 | 数值 |
| --- | --- |
| 端到端墙钟 | 182 ms |
| 吞吐 | 1648 篇/s · 52 725 张/s |
| 峰值堆 | 12.0 MB |
| 累计分配 | 32.8 MB |
| 纯解析 | 297 MB/s · 14 700 allocs/遍 · 6.31 MB/遍 |
| 事件数 | 7605 |

CPU 剖析（`go tool pprof -top`）显示：`runtime.cgocall` 占 78%（Windows 上所有系统调用
都走这条），其中 `os.Stat` 累计占 27%，而我们自己的解析 `mdscan.ScanLang` 只占 3.6%。
**结论：这一轮该省的是系统调用，不是算法。**

## 第 1 轮：少发系统调用（e2e 182 ms → 92 ms）

1. **同一路径的存在性检查只做一次**。原来每个图片引用都要 `os.Stat` 一次：一篇文档里
   同一张图被引用 30 次，就有 30 次 stat；9600 处引用实际只有 60 个不同的文件。
   改成按小写绝对路径缓存（`Runner.fileExists`），stat 从 9600 次降到 60 次。
2. **预扫并行化**。`run.started` 事件要带上每篇文档的图片数，原来这一步是串行读+解析
   所有文件，真正开始转换前先白等一遍；改成按并发数并行（至少 4 路）。
3. **写盘后不再多删一次**。`writeAtomic` 改名成功后临时文件已经不存在了，原来仍会
   `os.Remove` 一次（Windows 上要多花一次系统调用才报错）。

| 指标 | 第 0 轮 | 第 1 轮 | 变化 |
| --- | --- | --- | --- |
| 端到端墙钟 | 182 ms | **92 ms** | −49% |
| 吞吐 | 1648 篇/s | **3258 篇/s** | ×2.0 |
| 峰值堆 | 12.0 MB | 11.2 MB | −7% |
| 纯解析 | 297 MB/s | 297 MB/s | 未动 |

## 第 2 轮：新文件直接写（92 ms → 50 ms）

先用一个独立的小程序量了各种写法的代价（300 个 9 KB 文件，取 5 轮最好值）：

| 写法 | 每个文件 |
| --- | --- |
| 临时文件 + 改名（原实现） | 0.298 ms |
| 直接写（`os.WriteFile`） | 0.084 ms |
| `OpenFile(O_CREATE\|O_WRONLY\|O_TRUNC)` + 写 + 关 | 0.089 ms |
| 覆盖已有文件 + 改名 | 0.317 ms |
| 覆盖已有文件（直接写） | 0.083 ms |

原子写比直接写贵 **3.5 倍**，而绝大多数输出都是**新文件**（旁路模式旁边没有同名文件）。
所以改成：

- 目标不存在 → `O_CREATE|O_EXCL` 直接建了写（顺便保证不覆盖别人刚写的文件）；
- 目标已存在 → 仍然「临时文件 + 改名」，中途失败不会把原文件写坏——原地替换模式下
  那个「原文件」就是用户的源文档，这一步不能省。

再加一条：**内容一模一样就不重写**。目标已存在时先比一下内容，相同就直接跳过，
重复跑一次不会白改一遍文件时间戳（对 rsync / 编辑器 / git 都友好）。

| 场景 | 墙钟（最好 / 中位） | 吞吐 |
| --- | --- | --- |
| 基线（第 1 轮） | 92 ms | 3258 篇/s |
| 首次写入 | **50 / 51 ms** | **6037 篇/s · 19.3 万张/s** |
| 覆盖已有输出（内容相同 → 跳过写入） | **32 / 34 ms** | **9376 篇/s** |
| 只扫描分类（不写盘、不上传） | 16 / 17 ms | 18 624 篇/s |

并发扩展（假图床，假图床在 4 路就饱和了）：1 → 198 ms，2 → 152 ms，4 → 141 ms，
8 → 148 ms，16 → 150 ms。

## 真机 PicGo 验证

`http://127.0.0.1:36677`，每张图约 1 KB。既验功能也对并发做测量。

**功能**：3 篇文档 21 处引用（含远程图、行内代码、围栏代码块、缺失图片、反斜杠路径写法）
→ 输出 3/3 篇全部替换、残留本地引用 0、远程/代码块/缺失各保留 3/3、原文件一字节未动；
替换后的真实地址形如 `https://webp.mus.pp.ua/test_storage/20261109014515208.png`。

**并发（这是本轮最值钱的发现）**：

| 并发 | 图片数 | 墙钟 | 每张 |
| --- | --- | --- | --- |
| 1 | 8 | 4.948 s | 618 ms |
| 4 | 8 | 1.744 s | 218 ms |
| 8 | 8 | 1.585 s | 198 ms |
| 16 | 24 | 1.568 s | **65 ms** |

上传是纯等网络，`concurrency` 就是「同时在飞的请求数」。旧默认值 4 明显偏低，
8 相对 4 已经能省下可观时间，16 在图多时还能继续拉开（约 9 路有效并行后趋于饱和，
说明瓶颈在 PicGo/图床那一侧）。

## 第 3 轮：默认并发 4 → 8

- `internal/settings/settings.go`：`DefaultConcurrency = 8`；`Default()` 用它。
- 设置文件加 `schemaVersion`（当前 2）。加载到没有该字段的旧设置时做一次性迁移：
  并发仍是旧默认值 4 的，提到 8，然后写回。**迁移过之后用户再手动改回 4 就不会被动。**
- 前端占位默认值、CLI 帮助文案同步。

真实图床上的收益（同一批图，同一台机器）：并发 4 → 218 ms/张，并发 8 → 198 ms/张，
并发 16 → 65 ms/张。

### 顺带修掉一个用户数据级的 bug：设置文件带 BOM 就整份失效

`Load()` 原来把文件字节直接喂给 `encoding/json`，而 json 见到 UTF-8 BOM 会直接报错 →
凡是手工编辑过 `settings.json` 的用户（记事本保存 UTF-8 带 BOM，PowerShell 的
`Set-Content -Encoding UTF8` 也带 BOM），**所有设置会被静默重置成默认值**：
界面能打开、也不报错，只是选项悄悄变回了默认。现在 `Load()` 先过 `trimBOM()` 再解析，
`hasSchemaVersion()` 与 `migrate()` 吃的是同一份去过 BOM 的字节（否则迁移会反复触发），
并补了一条 `TestStoreToleratesBOM` 把这个行为钉死。

## 第 4 轮：上传结果缓存（重复运行不再重传）

**动机（真机测出来的）**：6 篇文档、59 处引用、39 张 150 KB 的图（共 8.85 MB），
第一次跑 **13.793 s**；把输出删掉再跑一次，**13 s 又全部重传了一遍**——
「改一篇文章、再跑一次」是最常见的用法，而每次都在重传没变过的图片。

**做法**（`internal/uploadcache`）：按「图床地址 + 图片绝对路径」记下上次得到的 URL，
图片的**大小与修改时间都对得上**才算命中；地址存在 `data/upload-cache.json`，
保留最近 4000 条、30 天过期（图床上的文件可能被删，过期就重传）；写盘时与磁盘上的
现有内容合并（界面与命令行可能同时开着）。设置里「复用上次的上传结果」默认开启，
命令行 `--no-reuse` 关掉，关掉时既不读也不写这个文件。

| 场景（假图床，300 篇 / 9600 处引用） | 墙钟 | 上传 | 复用 |
| --- | --- | --- | --- |
| 冷启动（无缓存） | 55 ms（最好），首轮 218 ms | 59 | 0 |
| 热启动（有缓存） | **53 ms** | **0** | **59** |

| 场景（真机 PicGo，6 篇 / 39 张去重图 / 59 处引用 / 8.85 MB） | 墙钟 |
| --- | --- |
| 冷启动（无缓存） | 13.793 s（同一配置另一次 27.656 s——图床波动很大，报数要带区间） |
| 同一进程热轮 | **10 ms → 2 ms** |
| **跨进程热启动**（新进程 + 同一个缓存文件，即「改一篇文章再跑一次」） | **3 ms** |

每次热启动的 `-verify` 都是 `输出文件=6 已全部替换=6/6 残留本地引用=0 远程保留=6/6
代码块保留=6/6 缺失保留=6/6`，而且缓存命中的地址照样写进了输出——**13.8 s → 3 ms 是
这一轮最大的一笔**。顺带一次 200 篇 / 4340 处引用 / 3856 次上传的真机跑：18.429 s、
`-verify` 200/200 全绿。

**踩到的坑（值得记）**：第一版把「跨运行缓存」的判断放在「本轮去重表」**之前**，
于是同一张图本轮第一次上传后立刻写进缓存，后续引用就被当成「缓存命中」——
冷启动那一轮报出 `reused=6853`（≈9600 处引用里所有同轮去重），数字完全失真。
正确顺序是：**先问本轮去重表（命中=复用），只有本轮第一个碰到这张图的 goroutine
才去问跨运行缓存（命中=缓存）**。修完冷轮 `reused=0`、热轮 `reused=去重图片数`，
并有 `TestUploadCacheSkipsSecondRun` / `TestUploadCacheDisabledBySettings` 钉住。

## 命令行这一侧已经到地板了

修完缓存顺序 bug 之后重新量了一遍（假图床，300 篇 / 9600 处引用 / 2.8 MB / 并发 8）：

| 场景 | 墙钟（中位） | 吞吐 |
| --- | --- | --- |
| 首次写入（`-fresh`，真建 300 个文件） | 122 ms | 2547 篇/s |
| 输出已存在且内容一致（跳过写入） | 35 ms | 9158 篇/s |
| 只扫描分类（`-dryrun`，不写文件） | 18 ms | 18290 篇/s |
| 纯解析（不写、不传） | 9.6 ms | 295 MB/s |

**首次写入多出来的那 85 ms，全是「建 300 个文件」的钱**（0.28 ms/个，见第 2 轮的
写盘微基准），解析占 10 ms、上传占 17 ms。并发扩展 1 → 149 ms，2 → 118 ms，
4/8/16/32 都是 117–118 ms：**并发 2 就饱和**，再加只是让峰值堆从 17.5 MB 涨到 28.3 MB。
`-cpuprofile` 也印证了这一点：`runtime.cgocall` flat 82.79%、
`internal/conv.createExclusive` cum 74.37%，而我们自己的代码最贵的是
`mdscan.protectedMask` 1.16% 和 `mdscan.ScanLang` 1.06%（cum 3.97%）。
**写文件被系统/杀毒实时防护串行化了，算法侧没什么可榨的。**

## 第 5 轮：命令行早就跑完了，是界面上不去

### 挖出来的真 bug

300 篇 / 每篇 32 张图 / 9528 处引用，图床用假图床（每张 5 ms）：命令行那一侧几百毫秒
就跑完（300/300 个输出文件写好、上传缓存 59 条、假图床计数停在 59、进程 CPU 冻结），
但**界面永远停在「转换中」**：取消按钮还在，状态统计停在「部分失败 248 / 待转换 44 /
上传中 8」，展开的文件明细也是残缺的。

根因在服务端的事件枢纽：每个订阅者是一个 **cap 512** 的 channel，投递用的是
`select { case ch <- ev: default: /* 前端读得慢就丢 */ }`。9500 条事件灌满 512 之后，
**连 `run.finished` 这种终止事件也会被丢掉**，前端于是永远等不到「结束」——
浏览器端被每张图一条的进度事件淹没了。

### 修法

1. **进度事件按文件合并**：每个订阅者只留「每个文件最新的那一条进度」，攒到要发别的
   事件（或读走）时按文件顺序落进队列，`file.finished` 永远不会排在自己的进度前面。
2. **终止事件永不丢**：队列到 4096 上限时从最旧的开始丢，但跳过
   `run.finished` / `run.cancelled`。
3. **一批事件一次写、一次 flush**：原来每条事件一次 `Fprintf` + `Flush`。
4. **前端按 16 ms 一批应用**（`setTimeout`，不是 `requestAnimationFrame`——窗口最小化
   时 rAF 不跑，定时器会跑，事件不会闷在缓冲里）。

### 复测（同一个 300 篇夹具，打包版 exe）

| 指标 | 修之前 | 修之后 |
| --- | --- | --- |
| 界面 settle | 永不到达（卡在进行中） | **432 ms** |
| 浏览器收到的 SSE 事件 | 9528 条且互相挤掉 | **1433 条** |
| 帧间隔 | — | 133 帧，最大 140 ms，只有 1 帧 > 100 ms |
| 最终数字 | 「替换 7500 · 复用 7239 · 失败 366」 | 「9600 张图 · 替换 8855 · 失败 445」，与命令行逐位一致 |

第二次（缓存热启动）**351 ms** settle，footer 多出「复用 59」，上传 0 次。
取消路径也复测了：慢图床（400 ms/张）跑到一半点取消，**13 ms** 界面就落定为
「已取消」。

回归钉在 `internal/server/hub_test.go`：客户端全程不读时终止事件仍在、进度只留最新的
那一条、丢最旧的也不会丢终止事件、退订后再推不 panic。

## 第 6 轮：默认并发 8 → 16（真机图床上的 2 倍）

上一轮把默认并发从 4 提到 8 时，手上只有 1 KB 的小图。这一轮换成真实尺寸
（150 KB，6 篇文档 / 59 张去重图）重新扫了一遍并发，用的是真 PicGo：

| 并发 | 最好 | 中位 | 每张 |
| --- | --- | --- | --- |
| 4 | 14.474 s | 14.807 s | 245 ms |
| 8 | 12.128 s | 12.825 s | 206 ms |
| **16** | **4.818 s** | **5.064 s** | **82 ms** |
| 24 | 4.802 s | 5.070 s | 81 ms |
| 32 | 5.012 s | 11.349 s | — |

交叉复测（8/12/16/20 各跑 3 轮、每轮 2 次取最好）也指向同一个结论：
8 → 8.8/9.2/10.0 s，12 → 5.9/7.9/8.9 s，**16 → 5.6/6.2 s**（另有一次 26 s 的离群），
20 → 5.3/5.7/6.0 s。**16 是拐点，再往上不多拿速度、只是在压图床**；并发 32 已经开始
抖动（出现 30 s 的轮次）。

远端图床本身的方差很大（中位能跳到 30 s 以上），所以这里看的是「最好」这一列——
它是我们能达到的地板。

`CurrentSchemaVersion = 3`，`migrate()` 把「还是上一版默认值」（4 或 8）的旧设置
提到 16（迁移写回后再改回去就不会被动）；CLI 帮助、界面输入上限、`docs/API.md`
与 `README.md` 的参数表同步。
## 第 7 轮：把界面拖进快车道（1000 篇不再卡顿）

前面几轮量的都是「解析 + 上传 + 写盘」，从第 5 轮开始发现：**图形界面下，浏览器那一侧
才是整条链路的瓶颈**。这轮专门量它、改它。

### 夹具与跑法

`%TEMP%\cmp-gui-1000`：1000 篇文档 / 每篇 12 处引用 / 共 12000 张图（`tools/bench -files 1000
-refs 10 -pool 60 -kb 4 -prose 2 -dryrun -keep`）。假图床 `tools/mockpicgo`（每张 5 ms），
界面用打包版 exe 起在 17982 端口，数据目录另给（`CMP_DATA_DIR`），
探针脚本 `tools/perf/gui-1000.mjs`（用 Playwright 的 `browser_run_code_unsafe` 跑：
把文件放到 MCP 允许的目录、脚本写成 `async (page) => {...}` 表达式）。

### 改之前

一次运行：**settle 1586 ms**，浏览器侧收到 4612 条 SSE，最长帧间隔 **489 ms**，5 帧超过 100 ms，
JS 堆 38.1 → 60.5 MB。卡顿的根源在 `web/src/composables/useRun.ts`：

- 每个事件都会让 `rowViews` 重算（`rows.map` 重建 1000 元素数组 + 1000 次对象展开）；
- `stats` 每次失效要遍历 1000 行、并对每行的 `result.items` 做 `filter` —— 一轮下来扫 12000 张图；
- `completedCount` 又一次 O(n) 遍历；`revealTarget` 依赖每一行的结果；
- `updateRow` 用 `findIndex` 找行（O(n)），`ensureRowFromResult` 用 `some` 再 O(n)；
- 点「开始转换」时行 id 从本地 `local-N` 换成服务端 id → **1000 个行组件整批卸载重挂**
  （顺带把用户展开的明细也收起来了）。

### 改了什么

- **结果直接挂在行上**：`RunRow.result`（`markRaw` 包住，避免把上万条明细变成响应式代理），
  行对象自己就是响应式单元 —— 某一行完成只重渲染那一行。
- `rowViews` 退化成 `rows.value.slice()`（只有增删行才重算）；页脚统计改成 `live` **增量计数器**
  （`file.progress`/`file.finished` 时增量加减，收到最终 `summary` 就直接用服务端的数字）。
- `rowIndex` + `eventIndex` 两张下标表：行 id（本地）与服务端 id 各查各的，`updateRow`/`absorbResult`
  都变成 O(1)。
- `applyStarted` 按路径复用已有行对象（只改字段），组件 key 保持稳定 →
  开始转换时不再整批重挂，展开的明细也不会被收起。
- Go 侧 `FileResult` 新增 `Reused` 字段（`runner.go` 的计数分支拆开，
  `StatusReused`/`StatusCached` 同样算「替换成功」但单独记 `Reused`），
  界面不必再为了显示「复用几张」去数上万条明细。

### 改之后

| 指标 | 改之前 | 改之后 |
| --- | --- | --- |
| settle（点开始 → 界面安定） | 1586 ms | **588 ms** |
| 最长帧间隔 | 489 ms | **162 ms** |
| 超过 100 ms 的帧 | 5 | **2** |
| 一轮收到的 SSE | 4612 | 4054（事件没少，只是不再逐条重算列表） |
| JS 堆峰值 | 60.5 MB | 39.6 MB |

页脚数字与命令行基准逐项一致（1000 个文件 · 12000 张图 · 替换 9837 · 失败 1163），
夹具里 1000 个 `.converted.md` 全部就位。

### 一条走不通的路（记下来别再试）

给行加 `content-visibility: auto` + `contain-intrinsic-size: auto 56px`，想让屏幕外的行
不参与布局绘制 —— 结果 **settle 从 746 ms 劣化到 3126 ms**（最差帧 1.6 s）。
原因是「56px」这个估计值离真实行高（约 90px）差太多，1000 个被 contain 的盒子让每次内容变化
都要重算包含块布局。回滚后恢复原值（同一个构建产物哈希）。要真省，得做虚拟滚动
（只挂可见的十几行），那是另一件事，目前 1000 篇 588 ms 的往返已经够用。

### 顺带记一笔测量口径

用 Playwright/CDP 采 CPU profile 时，**无障碍树的开销被算进来了**（自动化本身会常驻一棵
accessibility tree）：一轮 1.26 s 的 profile 里 `getTextAlternativeInternal` 117 ms、
`getCSSContent` 10 ms、若干 ARIA 计算合计约 145 ms；`(program)` 449 ms（样式/布局/绘制）、
`(idle)` 432 ms、GC 12 ms，而**我们自己的 JS 自耗时合计只有 50 ms 左右**。
真实用户在 WebView2 里跑（没有屏幕阅读器、没有自动化）时，这部分开销会小得多 ——
所以真机手感应当好于上表，上表是「带自动化开销」的偏悲观值。

## 第 8 轮：取消不是失败

按「取消」的时候，第一版实现会把每一个还没处理的文件都标成 `failed`：1000 篇文档、慢图床
（600 ms/张）跑到一半点取消，**1000 行全红**，页脚写着「失败 11000」。三处原因都在
`internal/conv/runner.go`：

1. 派发循环 `for i := range files { work <- i }` 不看 `ctx` —— 取消之后仍然把 1000 个文件
   逐个喂给 worker，每个都白走一遍空转的 `processFile`。
2. `processFile` 结尾把取消的文件写成 `FileFailed`，而它上面的计数 switch 已经把 10 个
   `StatusFailed` 图算进了 `res.Failed`。
3. `uploadGroups` 只要 `uerr != nil` 就把图标成 `failed`，不管这次失败是不是取消引起的。

### 改了什么

- 派发循环加 `if ctx.Err() != nil { break }`：取消之后一个文件都不再派，没轮到的文件保持
  空结果（界面把它们显示成「已取消」，它们确实一个字节都没被碰过）。
- 新增 `StatusCancelled`（图）与 `FileCancelled`（文件）：因取消而没传成的图记
  `StatusCancelled` 并计入 `Skipped`，不计入失败；被取消的文件状态是 `cancelled`，汇总里
  既不算成功也不算失败。
- `uploadGroups` 用 `upload()` 返回的状态，不再把取消一律压成 `failed`；`upload()` 自己在
  请求失败时也区分「取消」与「真的失败」。
- 前端补登记两个状态（`types.ts` 的联合类型、`FileRow.vue` 的 `FILE_STATUS_META` /
  `IMAGE_STATUS_META`）——服务端发一个前端没登记的状态，行状态会直接渲染不出来。

### 复测（1000 篇 / 12000 张图，假图床 600 ms/张，跑到 250 ms 时点取消）

| 指标 | 改之前 | 改之后 |
| --- | --- | --- |
| 取消 → 界面安定 | 280 ms | **135 ms** |
| 行状态 | 失败 ×1000 | **已取消 ×1000** |
| 页脚 | 替换 0 · 失败 11000 · 已取消 | **替换 0 · 失败 18 · 已取消** |
| 一轮推的事件 | 5025 条（`file.started` / `file.finished` 各 1000） | **105 条**（只碰了 17 个文件） |
| 落盘的输出 | 0 个 | 0 个（也没有残留的临时文件） |

那 18 个失败是**真的缺图**：夹具里每篇文档都故意放了一个不存在的 `images/missing.png`，
被碰过的文件如实报出来；剩下的 980 多个文件一个字节都没动。

回归钉在 `internal/conv/runner_test.go` 的 `TestCancelIsNotFailure`：第一次上传时就把 ctx
取消掉，断言汇总不标失败、被取消的文件不写输出、没轮到的文件结果为空、目录里 0 个
`.converted*`。

## 第 10 轮：5000 篇也不卡（文件级事件按文件合并 + 列表虚拟化）

第 7 轮把 1000 篇的界面往返从 1.6 s 压到 0.6 s，这一轮把语料加到 **5000 篇 / 60000 张图**
（`%TEMP%\cmp-gui-5000`，13.94 MB），一上来就撞出两个新的浏览器侧缺陷：

1. **行状态大面积撒谎**。页脚数字是对的（它来自 `run.finished` 的 summary），但
   `rowStatusCounts` 是 `{ 部分失败: 3343, 上传中: 16, 待转换: 1641 }` —— 1657 行永远停在
   「待转换 / 上传中」。根因是服务端订阅者队列 `subscriberQueueLimit = 4096`：5000 篇会产生
   10000+ 条**文件级**事件，队列灌满后按「丢最旧的普通事件」处理，而 `file.started` /
   `file.finished` 对界面来说就是结果本身，不是可有可无的噪声。那次浏览器只收到
   `file.finished` 3343 条。
2. **5.7 秒的单帧停顿**。5000 行 FileRow（每行 91.75 px）全挂在 DOM 里，任何一批事件都要
   patch 5000 个组件 + 浏览器重排/重绘整张 45.8 万像素的表。实测最差帧
   `[5702, 1675, 395, 332, 258, 224] ms`，>100 ms 的帧 11 个。

改法（两侧一起）：

- **服务端**：`file.started` / `file.progress` / `file.finished` 不再各自排队，而是共用
  「每个文件一个槽」的表，只留最新一条；槽攒到 `subscriberSlotBatch = 256` 条、或遇到
  run 级事件时，按首次出现顺序落进下发队列。这样事件总量从 ~10000 降到 ≤ 文件数，
  **每个文件的最终结果都不会被丢掉**。SSE 写出循环在没有终止事件时最多再等
  `sseFlushWindow = 40 ms` 攒一批，一批一次写、一次 flush。
- **前端**：事件按 `EVENT_FLUSH_MAX = 200` 条分片应用（不再一个 tick 里更新上千个组件）；
  文件列表**虚拟化**——只挂可视区上下各多 4 行的 FileRow，前后用占位块撑起滚动高度，
  行高实测（`ResizeObserver` + `data-row-id`）修正偏移表，滚动时二分定位。
- **兼容**：合并会改变事件的到达顺序，`file.finished` 找不到对应 id 时按 pathKey 认领已有
  的本地行，避免造出重复行。

5000 篇 / 60000 张图，假图床 5 ms/张，输出先删、上传缓存热（打包版 exe，Playwright 实测）：

| 指标 | 改之前 | 只改服务端 | 加虚拟化 | 再加 40 ms 攒批 |
| --- | --- | --- | --- | --- |
| 入队 5000 行 | 990 ms | 999 ms | 74 ms | **73 ms** |
| 一轮 settle | 9539 ms | 10759 ms | 2064 ms | **1873 ms** |
| 最差帧间隔 | 5702 ms | 4406 ms | 70 ms | **55 ms** |
| > 100 ms 的帧 | 11 | 22 | 0 | **0** |
| 浏览器收到的事件 | ~10600（且不完整） | 6647 | 20561 | **5625**（finished 5000 条全到） |
| 状态没更新的行 | 1657 | 0 | 0 | **0** |
| JS 堆峰值 | 106 MB | 273 MB | 33 MB | **28.6 MB** |
| DOM 里的行 | 5000 | 5000 | 11 | **11** |

1000 篇回归（同一台机器，同一探针）：settle **588 → 454 ms**、最差帧 **162 → 18 ms**、
SSE 事件 **4054 → 1130 条**、JS 堆 **39.6 → 11.9 MB**。

功能核对：页脚与命令行逐位一致（5000 个文件 · 60000 张图 · 替换 49200 · 复用 59 · 失败 5800）、
夹具里 5000 个 `.converted.md` 全部就位、`*.tmp*` 为 0、滚到底部随机抽看的行状态也都是
「部分失败」（探针会滚到底再数一遍，不能只信页脚）、抽检的 `doc-0000.converted.md` 替换正确。

回归钉在 `internal/server/hub_test.go`（客户端全程不读时每个文件的 finished 一个不少、
5000 文件 × 14 条事件合并后总数 ≤ 文件数+1、攒满 256 条就下发、同一文件只留最新状态、
跨批时进度仍排在自己的 finished 前面）。探针 `tools/perf/gui-scale.mjs` 与
`tools/perf/gui-1000.mjs` 一起进仓库，可复现上面两张表。

**测量方法的一个坑（值得记下来）**：`page.fill()` 往 textarea 灌 15 万个字符要 24.6 秒，
而且是平方级的（1000 行约 1 秒、5000 行 24.6 秒）——那是 Playwright 自己的开销，不是应用。
改成 `page.evaluate` 里直接赋值 + 派发 `input` 事件后 `fillMs = 1 ms`。第 7 轮记的
「入队+预览 1214 ms」也主要是这个开销。

## 第 11 轮：图床连不上就别干等

这一轮先做了四组「本来担心有问题」的实测，三组是负结果（行为正确，不需要改），
第四组撞上一个真问题。数字都在下面。

### 负结果：这些地方本来是好的

| 场景 | 实测 |
| --- | --- |
| GBK / UTF-16LE 文档 | `[失败] 文件不是 UTF-8 编码，暂不支持`，源文件一字未动、不留输出、不串码 |
| UTF-8（无 BOM）与 UTF-8（带 BOM） | 正常处理，带 BOM 的输出的 BOM **仍在**（前 3 字节 EF BB BF） |
| 80 字符深目录 + 60 字中文文件名 | 1 张图替换成功，接近 260 字符路径上限也没问题 |
| 单篇 5 MB 文档（6452 行 / 1250 处引用） | CLI **92 ms**、峰值工作集 **40.7 MB**；界面预览 12 ms、展开后行高 43 699 px、8735 个 DOM 节点，最差帧只有 52 ms |
| 空闲 30 秒 | CPU **0 ms**、工作集 56.6 MB、句柄 552，全程不变 |
| 1000 篇连跑 8 轮 | JS 堆稳定在 8.7 MB、DOM 节点 374、`EventSource` 始终 1 个（没有监听器泄漏） |

### 真问题：图床整体不可用时会干等几分钟

用户自建的存储（PicGo 里配的图床）某天不可达：PicGo 进程本身 200 正常响应，
但它把上传转发出去时 `ETIMEDOUT`。20 篇文档 / 59 张 300 KB 图的实测：

| | 改之前 | 改之后 |
| --- | --- | --- |
| 总耗时 | **259.5 s** | **64.9 s** |
| 失败图片数 | 320 处 | 81 处 |
| 用户看到 | 一张张慢慢失败，最后一片红 | `错误：连续 12 张图片上传失败（期间没有一张成功），已停止本次运行——图床多半连不上：http://127.0.0.1:36677` |

改法（`internal/conv/runner.go`）：连续失败计数 + 「这一轮成功过就不再触发」。
阈值定在 **12**：并发默认 16，一次批量请求本来就会同时压十几张图，
阈值太小时网络偶发抖动会误杀整轮；太大时用户又要多等好几轮超时。
触发后用运行自己的 cancel 把整轮掐掉，取消事件里带上汇总与原因，
界面弹红条、命令行打 `错误：…`，两边都能说出「为什么停了」。

顺带修的两处：

* 取消事件原来**不带汇总**，界面和命令行都没法说清原因（现在带上）。
* 命令行把每个文件的失败明细全打出来——5 MB 那篇文档同一张缺图被引用 100 次就是 100 行。
  现在每个文件最多列 20 条，多出来的折成一行 `……另有 N 处问题`。

## 第 12 轮：引用式图片终于能换了（补功能缺口，不是提速）

这一轮先量了命令行的 5000 篇端到端（假图床每次 5 ms）：

| 输出方式 | 墙钟 |
| --- | --- |
| 重定向到 NUL | 1680 ms |
| 重定向到文件（日志 1.96 MB） | 1679 ms |
| `--quiet`（只打汇总） | 1624 ms |

明细全打出来也只多花约 56 ms —— **输出不是瓶颈**，时间仍然花在建 5000 个文件上（与系统/杀毒实时防护串行，已到地板）。
所以这一轮不追速度，去补一个真实的功能缺口。

### 问题

引用式图片 `![alt][label]`（定义 `[label]: images/a.png` 写在文档别处）以前只提示
「本工具暂不处理」，于是整篇文档**一张图都不会被替换**。Typora、Obsidian 导出以及不少
README 都用这种写法，等于这些文档用不了这个工具。

### 改法

新增 `internal/mdscan/refs.go`：解析文档里的链接定义，并把三种引用式写法都认下来。

| 写法 | 替换区间 | 替换后 |
| --- | --- | --- |
| `![alt][label]` | `[label]` 那一段 | `![alt](地址)` |
| `![alt][]`（折叠） | `[]` 那一段 | `![alt](地址)` |
| `![alt]`（简写） | `]` 之后的插入点 | `![alt](地址)` |

* 标签比较忽略大小写、内部空白折叠；同一标签**以第一次定义为准**。
* 代码块/行内代码/注释里的「定义」不算数；`![alt](…)` 行内写法优先。
* 标签在文档里找不到定义时才提示（文案也改成说清楚这件事），否则不打扰。
* 地址里含空格或括号时，替换文本会包成尖括号，避免被当成「地址 + 标题」。
* 文档里的定义行**原样保留**（用户可能还有别的工具依赖它们）。
* 定义表**按需收集**：文档里没有引用式图片时，一个字节都不多扫。

### 数字

* 纯解析（300 篇 / 2.8 MB）：**306 / 314 / 304 MB/s、14700 allocs** —— 与第 9 轮（304/301/296）一致，
  没有回归（不用引用式写法的文档走的是同一条老路径）。
* 引用式压力夹具（85 KB、**2000 处引用式引用、5 张定义图**）：**46 ms**，2000 处全部就地内联化，
  残留引用式 0 处，5 条定义全部保留 —— 5 张图只上传了一次（去重照常生效）。
* `%TEMP%\cmp-paths` 夹具：doc-b 从「3 张成功」变「4 张成功，2 张失败」，整轮替换 14 → 17 处。

### 测试

* `internal/mdscan/scan_test.go`：`TestReferenceStyleResolves`（9 个用例：完整/折叠/简写/大小写/
  空白折叠/尖括号地址带标题/远程地址/没有定义只提示/代码块里的定义不算）、
  `TestReferenceStyleApplyMakesInline`（替换后是等价的整行写法）。
* `internal/conv/runner_test.go`：`TestReferenceStyleImagesAreConverted`（一篇文档里三种写法 +
  一个没有定义的标签，断言三处都换、定义行保留、没定义的那处不动）。

## 第 13 轮：`<pre>` / `<code>` 里的内容不再被误当图片

### 问题

围栏代码块、行内代码、HTML 注释早就跳过，但 `<pre>…</pre>`、`<code>…</code>` 之间的
内容没有跳过 —— 手写 HTML 的文档里，代码示例中的 `![x](img/c4.png)` 会被真的替换掉，
把示例改坏了（还顺手多传一张图）。实测：

```
<pre>
![四](img/c4.png)     ← 改之前会变成 https://…，改之后原样保留
</pre>
```

### 改法

`protectedMask` 增加一段：把 `<pre>`/`<code>` 到对应闭合标签之间的字节全部标记为受保护。
标签名大小写不敏感，且只认真正的标签边界（`<prefix>` 不会被误当成 `<pre>`）；
没有闭合标签时不标记，行为与从前一致。

### 性能（差点写坏）

第一版写成「逐字节扫全文，遇到 `<` 再比较」，两遍扫下来解析从 306 MB/s 掉到 247 MB/s（−20%）。
改用 `bytes.IndexByte(src[i:], '<')` 直接跳到下一个 `<` 之后回到 **299 / 303 / 310 MB/s、
14700 allocs**，与第 12 轮持平。教训：在解析热路径上，即使只是「顺带扫一遍」也要用
`IndexByte`/`Index` 这类 SIMD 跳转，别逐字节走。

### 测试

`TestScanMarkdown` 新增 4 个用例：`<pre>` 内忽略、`<code>` 内忽略、`<PRE>` 大小写、
`<prefix>` 不算 `<pre>`（仍然识别其中的图片）。

## 第 14 轮：文件系统边角上的说法（只读目标、输出目录是文件）

这一轮没有提速目标，去翻「文件系统边角」这一摊，看失败时到底跟用户说了什么。

### 负结果（本来就是对的）

| 场景 | 结果 |
| --- | --- |
| 路径总长 2834 字符（远超 260） | 正常转换（Go 的 os 包会自己加 `\\?\` 前缀） |
| `-o directory --out-dir <多级不存在>` | 正常创建并写出（目录模式保留原文件名） |
| 图床地址连不上（TCP 层） | 开跑前就拦下：2.2 秒报「无法连接 PicGo：端口未响应（地址）」，不会一张张干等 |
| `<img>` 各种写法（单引号/无引号/大写/`src=` 带空格/自闭合/属性在前） | 全部正确识别 |

### 改掉的两处

**1. 目标文件只读时，甩的是 Go 的原始错误**

改之前：`写入失败：rename C:\…\.cmp-3181963446.tmp C:\…\d1.converted.md: Access is denied.`
—— 临时文件名 + 英文系统调用信息，用户不知道该怎么办。

改之后：`目标文件是只读的，覆盖不了：C:\…\d1.converted.md（去掉只读属性后重试，或换个输出位置）`

实现：`writeAtomic` 里 `os.Rename` 失败后看一眼目标是否存在且没有写权限位，
返回一个 `errTargetReadOnly` 哨兵错误，由 `processFile` 换成上面这句人话（其它写入错误照旧带原始信息）。
原地模式同理：只读的源文件不会被硬闯。

**2. 「输出目录是一个文件」的报错重复两遍、还误导**

改之前：`无法创建输出目录：mkdir …\notadir: The system cannot find the path specified.: mkdir …\notadir: The system cannot find the path specified.`
（文案里嵌了 `%v`，外面又 `%w` 包了一次；而且 Windows 对「同名文件挡路」只会说「找不到路径」。）

改之后：`输出目录是一个文件，不是目录：C:\…\notadir`

顺带把这类「输出位置」问题搬进预检：`planOutput` 的错误以前在试运行里被丢掉
（`if p, perr := ...; perr == nil`），现在会写进预检结果的 `error`，
于是界面在按下「开始转换」之前就能告诉你位置选错了（中英双语都验过）。

### 测试

* `TestPreviewSurfacesBadOutputDir`：输出目录位置上是个文件时，预检必须带 `error`、且不给假输出路径。
* `TestReadOnlyTargetExplainsItself`（限 Windows）：只读目标要给出含「只读」字样的说明，而不是 rename 原文。

### 输出命名：同样一批文件，两次跑出来的名字会换人（真 bug）

`-o directory` 模式下不同目录里的同名文件（`a/post.md`、`b/post.md`）会自动加序号，
但序号是**在各自的工作协程里当场抢的**：`uniquePath` 只查「这一轮已经占用的名字」，
不看输入顺序，也不看磁盘上原来有什么。实测同一个命令连跑 6 次：

```
第 1 次：a → post.md   ；b → post-2.md
第 2 次：a → post-2.md ；b → post.md
第 4 次：a → post-2.md ；b → post.md
第 5 次：a → post.md   ；b → post-2.md
```

两个后果：① 同一批文档两次导出的**文件名会互相串**（上次编辑的 `post-2.md` 这次是另一篇），
版本管理里看着像整批改名；② **预检显示的输出路径未必是真的**——预检和真跑是两次独立的规划，
各抢各的名字。

改法：开工前按**输入顺序**把这一轮所有输出路径一次定好（`planOutputs` → `reserveOutput` 查计划），
预检和真跑走同一份规划。实测：

* 30 个同名文件，连续 6 次真跑，`a → post.md`、`b → post-2.md` … 每次都一样；
* HTTP 预检给出的 30 个名字与随后 `/api/run` 真正写出的 30 个文件**完全一致**。

### 测试

* `TestOutputNamesAreDeterministic`：12 个同名文件，预检两次 + 真跑两遍，输出路径都必须按输入顺序
  （临时把预计划那一行去掉，这条用例立刻失败——它确实在守着这个 bug）。
* 目录文案与 `KeyConvPathIsDir` 走的是既有的端到端用例与人工核对。

## 第 19 轮：两处「用户改不动、也看不见」的边角

这一轮不是提速，是把两个安静的坏行为说清楚。

### 一、设置文件坏了，用户一点都不知道

第 3 轮修过「设置文件带 BOM 就被当成解析失败」的 bug，但**解析失败本身的处理**没动过：
`Load()` 直接 `return Default()`，于是用户手改过 `settings.json`（少个引号、多个逗号）之后，
自己设的图床地址、并发数会**凭空变回默认值**，界面上没有任何提示——他只会觉得「这软件记不住设置」。

现在：读不出来时把原文件另存为 `settings.json.broken`（已存在就不覆盖，第一份才最接近「本来
长什么样」），并把这件事说给用户听：

| 出口 | 说法 |
| --- | --- |
| 图形界面 | 「关于」里一条红色提示：`设置文件读不出来（不是合法的 JSON），已改用默认值。 原文件另存为 …settings.json.broken，改好它可以恢复设置。` |
| `/api/health` | 新增 `settingsNote` 字段（英文请求返回英文） |
| 命令行 | 开头一行 `提示：设置文件读不出来…`（在 `Load()` 之后打印——Load 才是发现问题的动作） |
| 磁盘 | 原文件被复制成 `settings.json.broken`，改好它就能恢复设置 |

实测（`CMP_DATA_DIR` 指向一个装着 `{ this is not json` 的目录）：CLI 打印上面那句提示、
`.broken` 里是原始字节、`/api/health` 的 `settingsNote` 中英各自正确、改回合法 JSON 后提示消失。

### 二、两个 `/api/run` 会各自开一个 Runner

`handleRun` 原来只管把 `cancel` 记进 `s.runs`、起一个 goroutine，**没有「已经在跑」的判断**。
界面因为 `busy` 挡住按钮，正常点不出来；但 `/api/run` 是文档里公开的接口，脚本连发两次、或者
两个窗口一起点，就会有两个 Runner 同时处理同一批文件：同一张图被传两遍、同一份输出被两边
反复写（原子写保证不写坏，但结果与统计会互相打架），而界面只有一套进度可显示。

现在同一时刻只允许一次：第二次请求返回 `409`，错误码 `conflict`，消息「已经有一次转换在跑，
等它结束或先取消再试」。`codeFor` 里补了 409 → `conflict`（原来落到默认的 `error`）。

回归测试两条：`internal/settings` 的 `TestStoreReportsBrokenFile`（坏文件 → 默认值 + 提示 +
`.broken` 字节一致 + 第二次读取仍指出位置 + 改好后提示消失 + 英文提示不含中文）、
`internal/server` 的 `TestRunRejectsConcurrentRun`（图床卡住不返回时，第二次 `/api/run` 得到 409
且带 `conflict` 消息）。实测也各跑了一遍：`/api/health` 给出 `settingsNote`，慢图床下第二次
`/api/run` 得到 `HTTP 409`。
## 第 20 轮：文件被别的程序占着时，别再打印系统原话

顺着第 14 轮「失败说法」那条线继续往下查，这次盯的是**文件被占用**——真实场景很常见：
用户把 `.converted.md` 开着看、或者在 Typora / Word 里开着源文档，又点了一次转换。实测两种：

| 情况 | 改之前的说法 |
| --- | --- |
| 输出文件被占着（生成副本模式） | `写入失败：rename …\.cmp-2853839841.tmp …\a.converted.md: Access is denied.` |
| 源文件被占着（原地模式） | `无法读取文件：open …\b.md: The process cannot access the file because it is being used by another process.` |

第一句尤其糟：它把**随机命名的临时文件**摆到用户面前，还只说「Access is denied」——
用户根本不知道是谁在拒绝什么。两句现在都换成了：

```
[失败]  a.md   写不进去：文件正被别的程序占用，或者没有权限：…\a.converted.md（关掉占用它的程序再试）
[失败]  b.md   读不出来：文件正被别的程序占用，或者没有读取权限：…\b.md（关掉占用它的程序再试）
```

### 一个 Go 的坑：共享冲突不在 fs.ErrPermission 里

写不进去那条容易修：`writeAtomic` 的 rename 失败后已经会 stat 目标，加一条
`errors.Is(err, fs.ErrPermission)` 就够了。但**读**那条光靠 `fs.ErrPermission` 抓不到——
Windows 给的是 `ERROR_SHARING_VIOLATION(32)`，而 Go 的 `syscall.Errno.Is` 只把
`ERROR_ACCESS_DENIED(5)` 映射到 `fs.ErrPermission`。实测（直接构造 Errno）：

```
Errno(5)  -> fs.ErrPermission=true    # Access is denied
Errno(32) -> fs.ErrPermission=false   # 文件被别的程序占着
Errno(33) -> fs.ErrPermission=false   # 区域被锁
```

所以新增了 `platform.IsBusy(err)`：Windows 上认 5 / 32 / 33，其它平台就是权限错误。
（`syscall` 包没给这两个常量，`golang.org/x/sys/windows` 里有，但 `internal/platform`
一直坚持「不引 cgo、不引第三方库」，所以按数值定义并用注释标明出处。）

### 回归测试

`internal/conv/runner_windows_test.go`（新增，`//go:build windows`）两条用例：用
`syscall.CreateFile(..., dwShareMode=0, ...)` 把文件锁住（`os.OpenFile` 不行，Go 默认
允许共享读写删除），再跑一轮，断言错误文案里有「占用」且**不含 `.tmp`**。
把 `platform.IsBusy` 换回 `errors.Is(err, fs.ErrPermission)` 之后 `TestLockedSourceExplainsItself`
立刻失败，说明它确实守着这个修复，不是空跑。

顺带复核：只读目标仍然走第 14 轮那句「目标文件是只读的，覆盖不了」；内容没变时
「跳过写入」的快路径也仍然不报错（只读目标只有在新内容确实不同时才会被写）。
## 第 21 轮：更新完之后，界面不再停在「正在重启」

前 20 轮量的都是转换链路，这一轮把「更新」这条路径从头到尾在界面上演练了一遍
（第 16 轮只演练了 API）。

演练环境：`%TEMP%\cmp-fileserver.exe` 在 36681 上服务清单 `version.json`（9.9.9，
sha `4998381a315e…`，size 14,367,744）和 `candidate.exe`（用
`-ldflags "-X …/internal/version.Version=9.9.9-test"` 编出来的假新版本）；
把当前 exe 复制到 `%TEMP%\cmp-update-gui\`，带
`CMP_UPDATE_MANIFEST=http://127.0.0.1:36681/version.json` 在 17998 上跑。
探针：`tmp-update3.mjs`（仓库外的一次性脚本，思路在下面）。

### 第一次演练：装是装上了，页面不动

状态走得很顺：`有新版本可以更新` → `正在下载 0%` → `正在重启，界面马上会重新打开`，
3 秒后同一个端口 17998 的 `/api/health` 已经报 `9.9.9-test`，exe 也换成了
14,367,744 字节 —— **但浏览器里那一页永远停在「正在重启」**。
原因：`useUpdate` 的轮询在重启期间请求失败就静默停了，谁也没告诉页面「新版本已经起来了」。

### 改法

`install()` 记下装之前的版本号，然后 `waitForRestart()` 每 700 ms 问一次
`/api/health`，**只在版本号真的变了的时候** `window.location.reload()`
（最多等 90 秒）。只认「版本变了」这一个信号，是因为重启中途端口会短暂不可用，
而旧进程也可能还在应答同一个版本 —— 这两种都不该触发刷新。

### 第二个坑：拿两个格式不同的版本号直接比字符串

第一版写的是 `health.version !== wasVersion`。实测**页面 312 ms 就刷新了，刷完还是 v1.0.0**：

* 界面上的 `current` 是 `v1.0.0`（短格式，底栏就显示这个）
* `/api/health` 报的是 `1.0.0 (4cc55e4)`（带提交号）

两个字符串永远不相等，于是页面在**旧进程还占着端口**的时候就刷新了一次，
刷回来当然还是旧界面。改成先取出数字部分再比（`versionCore()`）之后：

| | 直接比字符串 | 取数字部分再比 |
| --- | --- | --- |
| 刷新时刻 | 点完 312 ms（旧进程还活着） | 点完 934 ms（新进程已接管） |
| 刷新后页脚 | `v1.0.0`（还是旧的） | **`v9.9.9-test`** |
| exe | 14,367,744 字节 | 14,367,744 字节 |

两次演练的完整状态流都是 `有新版本可以更新` → `正在下载 0%` →
`正在重启，新版本起来后界面会自动刷新`，区别只在刷新后看到的是哪个版本。

### 顺带确认的

* 桌面窗口形态不受影响：旧进程退出、新进程开新窗口，页面刷不刷新都无所谓。
* 更新期间「关于」弹窗里的按钮是锁住的（`locked`），下载百分比会走。
* 演练用的 exe 是复制的副本，所以整个演练不碰仓库里的 `bin\convert-md-picture.exe`。
## 第 22 轮：图床限流（429 / 503）不再被当成「图床挂了」

前几轮把"图床整个连不上"和"文件被占用"都照顾到了，但漏了一类很常见的情况：
图床**活着**，只是回答 429（请求太频繁）或 503（暂时不可用）。
原来的代码里，只有 `>= 500` 才算「可重试」，其余非 200 一律直接判死：

```go
if resp.StatusCode >= 500 {
    return "", true, ...   // 重试
}
if resp.StatusCode != http.StatusOK {
    return "", false, ...  // 直接失败（429 走的就是这条）
}
```

于是 429 立刻变成一张图的失败。更糟的是它会喂给第 11 轮那个熔断器：
连续 12 张失败 + 整轮没成功 ⇒ 掐掉整轮，并报「图床多半连不上」——
**而图床明明是通的，还在好好回 JSON**，这句话会把用户带向完全错误的排查方向。

### 改法

1. **429 / 503 可以重试**，并且读 `Retry-After`（秒数或 HTTP 日期都认）。
   解析不出来就自己退避 1 秒；单次最多等 10 秒（再长就不礼貌了，用户可以随时取消）。
2. **冷却闸门是全体共享的**：一个协程被限流，其它 15 个也不会继续撞上去——
   都是同一个 `Client`，把「可以再发了」的时刻记在客户端上（`gateUntil`），
   每个请求发出去之前先过一道 `waitTurn`。没有冷却时这一步几乎不花时间。
3. **限流有自己的重试预算**（5 次），不复用普通失败的 2 次：
   图床是活的，多等两轮很正常。
4. **限流不再算进「图床挂了」的熔断**。另起一条线（`limitStreak`），
   一直限流时给的是另一句话：

   > 图床一直回「请求太频繁」（连续 12 张没成），已停止本次运行——它是通的，过一会儿再试，或把并发调小：<地址>

### 实测（`bin\convert-md-picture.exe`，假图床 `tools/mockpicgo`）

给假图床加了 `-ratelimit <n>`（前 n 次请求回 429）和 `-retry-after <时长>`，
用四个不同端口的实例做前后对照，夹具是 6 篇 / 13 篇各带一张图的文档。

**场景 A：偶发限流**（前 3 次请求 429，6 篇文档）

| | 改之前 | 改之后 |
| --- | --- | --- |
| 替换链接 | 3 处 | **6 处** |
| 失败 | 3 处 | **0** |
| 真正写出来的文件 | **3 个**（另外 3 篇「所有本地图片都处理失败，未生成文件」） | **6 个** |
| 用时 | 0.0 s | 1.0 s |

一次限流就让一半文档彻底没生成；改完之后这 3 次限流被重试救回来，`doc-00.md` 里已经是
`![x](https://mock.local/doc-00.png)`。

**场景 B：一直限流**（前 100 次请求 429，13 篇文档）

| | 改之前 | 改之后 |
| --- | --- | --- |
| 用时 | 0.0 s | 4.0 s（每一轮都按 Retry-After 等了） |
| 结果 | 失败 11 个 · 已取消 | 失败 8 个 · 已取消 |
| 说法 | 「…已停止本次运行——**图床多半连不上**：<地址>」 | 「…已停止本次运行——**它是通的**，过一会儿再试，或把并发调小：<地址>」 |

两边的耗时都不到一眨眼是因为熔断器（12 张）很快就到了；区别在于改完之后它先认真重试、
再给一句能照着做的结论。

### 回归测试

`internal/picgo/picgo_test.go`：429 会重试而不是判死（`TestUploadRetriesWhenRateLimited`）、
503 同样重试、`Retry-After: 1` 真的等满 1 秒（`TestUploadHonorsRetryAfterSeconds`）、
一直限流时试满限流预算才报错、冷却闸门挡住其它上传（`TestCooldownGateBlocksOtherUploads`）、
取消时 `waitTurn` 立刻返回、`parseRetryAfter` 的八种输入（含秒数、HTTP 日期、过期日期、垃圾值）。

`internal/conv/runner_test.go`：一直限流时给的是「请求太频繁」而**不是**「连不上」
（`TestAbortsWhenEndpointRateLimits`）、偶发限流（前 3 次 429）该被重试救回来一张不失败
（`TestRateLimitBurstIsRetriedNotFailed`）。

反证过：把 429/503 那个分支改成 `if false`，`TestUploadRetriesWhenRateLimited` 立刻失败，
报的正是老行为「PicGo 返回 429: slow down」。这两个用例的等待时间加起来约 8 秒
（限流重试就是要等），所以 conv 包的测试从 1.5 秒变成 9.6 秒——值得。
## 第 23 轮：每条设置「真的生效了吗」矩阵

前面二十几轮都在改代码，这一轮换个方向：**把用户能拧的每个旋钮都拧一遍，看它是不是真的接在
该接的地方**。理由是设置项最容易出现「界面存下去了、后端没读」或者「文案说的和实际做的不一样」，
而这种问题平时不会有人发现，只会让人觉得「这软件有点怪」。

夹具 `%TEMP%\cmp-matrix-src`：两篇文档，各有一张真图（`img/one.png`）、一张远程图、一张缺图；
每个用例把它复制到干净的目录里再跑，图床用 `tools/mockpicgo`（36678，每张 5 ms）。

| 设置 | 期望 | 实测 |
| --- | --- | --- |
| `output=sidecar`（默认） | 原文件旁边生成 `a.converted.md` | ✓ 生成 `a.converted.md` / `b.converted.md`，源文件一字未动 |
| `-s -done`（自定义后缀） | 用 `-done` 而不是 `.converted` | ✓ 生成 `a-done.md` / `b-done.md` |
| `-s .md`（后缀写成 `.md`） | 规则是「原名 + 后缀 + `.md`」 | ✓ 生成 `a.md.md`——不好看但符合规则（想覆盖原文件请用 `--in-place`） |
| `output=in-place` + 备份（默认开） | 覆盖原文件、留下 `.bak` | ✓ `a.md` 里已换成 `https://mock.local/one.png`，`a.md.bak` 里还是 `img/one.png` |
| `output=in-place` + `--backup=false` | 覆盖原文件、不留 `.bak` | ✓ 目录里只有 `a.md` / `b.md` |
| `output=directory` + `--out-dir` | 全部输出到指定目录、保留原文件名 | ✓ 源目录只有 `a.md`/`b.md`，输出目录里是 `a.md`/`b.md`（已转换） |
| `output=directory` 但不给 `--out-dir` | 说清楚缺什么 | ✓ 开跑前就报「参数有误：输出到目录时必须指定目录」 |
| `--dry-run` | 不上传、不写文件 | ✓ 目录里还是两篇原文档 |
| `--retries n` | 每张图最多试 n+1 次，退避 300/600/1200 ms | ✓ 见下表 |
| `-c n` | 同时上传的图片数 | ✓ 见下表 |
| `endpoint` / `reuseUploads` | 上传到该地址 / 不再重传 | 前几轮已单独验过（含带尾斜杠、少写 `http://`） |

**重试次数**：为了数请求，写了个一次性小工具 `%TEMP%\cmp-count500.exe`（所有上传都回 HTTP 500，
`/stats` 报收到多少请求）。两篇文档引用的是**同一张图**（去重后只有 1 次上传），所以请求次数
应当正好等于 重试次数 + 1：

| `--retries` | 图床收到 | 用时 |
| --- | --- | --- |
| 0 | 1 次 | 0.0 s |
| 1 | 2 次 | 0.3 s |
| 2 | 3 次 | 0.9 s |
| 3 | 4 次 | 2.1 s |

用时 0.3 / 0.9 / 2.1 秒正好是 300ms、+600ms、+1200ms 的累加，退避也对得上。

**并发数**：8 篇文档各引用一张不同的图（8 次上传），图床每张慢 200 ms，那么总耗时应当接近
`8 × 200ms ÷ 并发`：

| `-c` | 实测 | 理论下限 |
| --- | --- | --- |
| 1 | 1645 ms | 1600 ms |
| 2 | 833 ms | 800 ms |
| 4 | 432 ms | 400 ms |
| 8 | 232 ms | 200 ms |
| 16 | 232 ms | 200 ms（只有 8 张图，再高的并发没有活干） |

一条不差，说明这个数字确实是「同时在飞的请求数」。

### 顺手修掉的两处文案不一致

矩阵跑完发现同一个设置在三处被描述成三样，而且界面上写的范围和实际允许的范围对不上：

- 设置界面里「并发数」右边的范围提示还是 **`1 – 16`**，而输入框的 `max` 和保存后的校验都是
  **32**（第 6 轮把上限从 16 提到 32 时漏改了这一处提示）。
- `--help` 的短说明写「同时处理的文件数」，长说明写「同时上传的图片数」，界面上写「并发数」。
  实际这个数字同时决定**文件工作池**和**上传信号量**（`internal/conv/runner.go` 里
  `workers := r.cfg.Concurrency` 与 `upload()` 里的 `r.sem`），所以统一改成
  「同时处理的文件数，也是同时上传的图片数」，并在界面上加了一行小字说明。
