# Build & development

[English](build.md) | [简体中文](build.zh-CN.md) · back to [README](../README.md)

## Requirements

Go 1.24+ to build the binary. Changing the UI also needs Node 20.19+ and pnpm —
the build scripts run `pnpm --dir web install` for you.

## Commands

Run from the repository root:

| Command | What it does |
| --- | --- |
| `npm run build` | build the frontend, then `bin/MarkPic.exe` |
| `npm run build:go` | compile Go only (needs an existing `internal/ui/dist`) |
| `npm run start` | Vite on 5173 plus a window with hot reload |
| `npm run start:mock` | same, against a fake image host instead of PicGo |
| `npm run test` | `go test ./... -count=1` |
| `npm run typecheck` | `vue-tsc --noEmit` only |

`internal/ui/dist` is not committed: it is the `go:embed` input. `build`, `start` and
`test` rebuild the frontend automatically when the output is missing. Plain
`go run ./cmd/markpic` works too, but also needs `internal/ui/dist` to exist first.

## Repository layout

| Path | Contents |
| --- | --- |
| `cmd/markpic` | entry point, single instance, native window, bridge, title bar |
| `internal/app` | bridge method table and events |
| `internal/mdscan` | Markdown scanning and byte-range replacement |
| `internal/imgpath` | classifying and resolving image addresses |
| `internal/picgo` | PicGo upload client |
| `internal/conv` | conversion pipeline |
| `internal/remoteimg` | remote image checking and downloading |
| `internal/remotecache` | download cache |
| `internal/uploadcache` | upload cache |
| `internal/settings` | reading and writing settings |
| `internal/platform` | native dialogs, ANSI code page |
| `internal/update` | update check and install |
| `internal/ui` | embedded frontend output (`go:embed`) |
| `web` | Vue 3 + TypeScript + Vite frontend |
| `scripts` | build, start and test scripts |
| `tools/bench` | benchmarks |
| `tools/mockpicgo` | fake image host |

Icons live in `assets/`. Normal builds reuse the committed `.ico` and `.syso` files, so
they are not regenerated.

## Branches and releases

- Development happens on `dev`. `main` only receives merges from `dev`, and a
  protected-branch rule enforces it.
- A merge to `main` triggers **构建并发布**. It runs only when the diff touches
  `cmd/`, `internal/`, `web/`, `scripts/`, `assets/`, `tools/`, `go.mod`, `go.sum` or
  `package.json` — documentation-only merges do not ship a release.
- The version is the release date (CalVer, `Asia/Shanghai`); a second release on the
  same day becomes `2026.11.17.1` and so on, discovered from tags.
- A commit subject containing `[no-release]` builds and tests, but publishes nothing.
- The release carries the executable plus `version.json`, the manifest that clients
  read to find updates. Nothing is pushed back to the repository. The manifest also
  carries `notesBody`, the full release notes the in-app “What's new” dialog shows.
- Release notes are generated by `scripts/release-notes.mjs` from the commits since the
  previous tag. Preview them locally with:

```bash
npm run notes -- --version 2026.11.17 --dry-run
```

A `同步 main 到 dev` workflow merges `main` back into `dev` after every merge, and
`主从同步检查` blocks a pull request whose branch does not contain the latest `main`.
